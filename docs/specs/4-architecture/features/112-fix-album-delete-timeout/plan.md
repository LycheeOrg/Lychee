# Feature Plan 112 – Fix Album Delete Timeout

Linked specification: [spec.md](spec.md). Tasks: [tasks.md](tasks.md). Status: implemented, I12 (FR-112-14) analysis and drift gates passed 2026-11-27. Updated: 2026-11-27.

## Vision & Success Criteria
Deleting a 4000-photo album or a 4000-photo selection returns once the DB transaction commits. File deletion runs in bounded jobs (≤500 paths). On `sync`, the jobs the delete code starts (files, person stats, face embeddings, thumbs) and the delete webhooks run after the response. A multi-photo delete dispatches each thumb-refresh job once and fires `PhotoWillBeDeleted` only for `photo.delete` webhooks. No query of a delete request, permission checks included, binds more than 1000 parameters. Sold size variants are kept with NULL-safe SQL and detached in every delete path, so rotating a photo with a sale works. A migration re-links the sold variants the old update detached from photos that still exist. A force delete handles each chunk of photos from start to end, so on a slow disk with a small buffer pool the rows of a chunk are read once (FR-112-14). The request still grows with the number of photos (Q-112-13, follow-up feature).

## Assumptions & Risks
- The affected-album set must be resolved before the DB delete: `photos_tags`, `faces` and `album_user_thumbs` rows of the deleted photos are gone afterwards (cascade). Jobs are dispatched after it, so on `sync` they cannot re-pick a photo being deleted.
- `lychee:sync` deletes photos and albums from the console (Import `DeleteMissingPhotos` / `DeleteMissingAlbums`). `afterResponse()` there runs on `$app->terminate()` when the command exits, so deferred jobs pile up in memory for the whole run (bounded by paths) and run at the end. Accepted.
- Each after-response job runs inside `rescue(report: true)`: a failing batch is reported and the others still run. This is framework behaviour (`Dispatcher::dispatchAfterResponse()`), read in the vendor code and not re-tested here.
- On `sync`, person counts and smart/tag/person thumbs are refreshed a moment after the response; a read issued right after it can still see the old values (accepted, Q-112-06 A).
- HTTP feature tests call the kernel's `terminate()` inside the request helper, so after-response jobs run before the test's assertions. Unit tests that call an action directly do not terminate the app; they observe deferred jobs only through `Bus::fake` (`assertDispatched` also counts after-response dispatches). No existing direct-call test asserts deleted files or these jobs.
- With `sync`, file I/O after the response still counts against FPM's `request_terminate_timeout`, and under Octane against `LYCHEE_MAX_EXECUTION_TIME` (default 30 s, wall clock), since Octane terminates the app inside the request handler. Accepted (Q-112-01 A cons). The same holds for every after-response job. If the worker is killed, the rest of the in-memory list is lost: unsent delete webhooks, orphaned files (`lychee:ghostbuster`, active upload disk only), stale person stats and face embeddings. Accepted as best effort (Q-112-10 A). Webhooks run first because they are dispatched before the DB delete.
- `album_user_thumbs` rows pointing at a deleted photo are cascaded away; that viewer's thumb is recomputed lazily on next read, as today.
- FR-112-11 changes the `AlbumPolicy` helpers that the move-by-id checks share. Their results must stay identical; existing move and delete request tests guard it.
- FR-112-10 changes shop data behaviour: sold variants of photos that are not deleted keep their `photo_id` (today they lose it), and `SizeVariant\Delete` detaches sold variants instead of keeping them on the photo (Q-112-08 A). After a rotate, the buyer downloads the pre-rotation file.
- FR-112-13 is a data repair on shop data. No test (owner rule): it is run on the dev DB before the commit (S-112-22). Lychee runs migrations on update, so the repair happens on upgrade. Rows blocked by `unique(photo_id, type)` stay detached, with row and file kept.
- FR-112-12: a delete webhook is still sent when the DB delete then fails, as today (the event fires before the delete).
- FR-112-14 lowers the request cost on slow disks but does not bound it: on the 2026-11-27 server the first read of a chunk still costs about 1 s per 500 photos, and the deletes change about 17 index entries per photo. The gain is checked by a second `DB_LOG_SQL` run on that server (owner). The end state is Q-112-13's follow-up feature.

## Release Note
- Deleting large albums or large photo selections does less work in the request: files are deleted in batches of at most 500 paths (after the response on `sync`), the rows of each chunk of photos are read once, and requests with more than 1000 ids no longer fail on MySQL. On a slow disk a very large album can still reach the request time limit: a background delete is planned.
- Rotating a photo with sales works again. Sold size variants are kept for the buyer and detached from the photo. An upgrade migration re-links sold size variants that an earlier photo delete detached from photos that still exist.
- With the `sync` queue, file cleanup, person statistics, face embeddings, album thumbs and `photo.delete` webhooks run after the response, on a best-effort basis: if the PHP worker is stopped before they finish, the rest is dropped. `lychee:ghostbuster` removes leftover files on the active upload disk. On an S3 install, track files left on the local disk are removed by hand. An asynchronous queue stores each job when it is dispatched, so a stopped worker drops none, but a failed webhook call is still not retried.
