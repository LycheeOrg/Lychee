This feature applies the existing Struct-of-Arrays convention (ADR-0009) and the existing `bucket_id`-driven virtual-scroll pattern (Feature 061/062) — it does not establish a new convention, so no new ADR is added.

## Overview

Feature 057 established the flat, `toBase()`-queried Struct-of-Arrays (SoA) response convention (ADR-0009). Feature 061/062 applied it — plus a materialized `bucket_id`-driven virtual-scroll backend (buckets / children-data / rights) — to **sub-albums and root albums**. Photos are the one remaining major listing surface still served exclusively by the fully-hydrated, paginated v2 path (`GET /api/v2/Album::photos`, `AlbumPhotosController::get()` → `PhotoRepository::getPhotosForAlbumPaginated()` → `PaginatedPhotosResource` wrapping a full `PhotoResource` per photo — ~26 fields including all 9 size variants, EXIF, palette, statistics, rating — per the `virtual-scrolling-study.md` finding, lines 321-341). At the confirmed real-world scale (~700,000 photos across ~7,000 albums, individual albums reaching five-figure photo counts), this is both the heaviest per-row payload and the largest per-parent row count in the codebase — worse on both axes than the sub-album case Feature 061 solved.

This feature ports the SoA + bucket contract to **photos directly inside one album**, per user direction, as a three-tier split (naming chosen by the user):

1. **`buckets`** — bucket counts + labels for the album's own direct photos, mirroring `GET /Albums/{album_id}/buckets` exactly in spirit.
2. **`ratios`** (served at the bare `GET /Albums/{album_id}/Photos` path, mirroring how tier 2 for albums sits at the bare `GET /Albums/{album_id}` path with no suffix) — the minimal whole-album-at-once render data a grid/justified-layout consumer needs: id, aspect ratio, bucket_id, video/raw/live-photo/highlighted/validated flags, owner, dates, plus a handful of config-gated fields (rating, title-or-description overlay text, tags) mirroring exactly which v2 fields the equivalent tile already conditionally renders (see FR-064-07/FR-064-18). **Not** paginated — the `virtual-scrolling-study.md` (lines 374-432) already worked out that an SoA-shaped `{id, ratio}`-class payload costs ~140KB at 10,000 photos, comfortably safe as a single response, which is the direct rationale for keeping this tier un-chunked like Feature 057/061's own "never paginate" precedent.
3. **`details`** — the information needed **when the user is about to open a photo** (per user direction) — description, tags, rating, license, EXIF-lite, owner, and watermark-aware size-variant URLs for every variant the lightbox needs (see FR-064-19) — deliberately **not** whole-album-at-once (unlike tier 1/2) — scoped to either one bucket or an explicit, size-capped id list, per the user's own framing ("the details for the current album/bucket"), since this tier's per-photo payload is heavy enough that a five-figure album would make an unbounded response expensive again.

**A structural correction this feature makes to a naive "just copy Feature 061" approach**: `Album.bucket_id` (Feature 061) lives on the `albums` row itself because every album has exactly one parent (`parent_id`, a tree edge). Photos do **not** have this property — `photo_album` is a genuine many-to-many pivot (composite primary key `(photo_id, album_id)`, confirmed via `database/migrations/2025_05_28_201707_create_photo_album_pivot.php:22-29`), and `App\Actions\Photo\MoveOrDuplicate::do()` (`app/Actions/Photo/MoveOrDuplicate.php`) explicitly supports **copying** a photo into a second album while it keeps its original album link (the "duplication" case, `$from_album === $to_album`... no-op, vs. copying into a genuinely different `$to_album` without deleting the `$from_album` row — see `CopyPhotosRequest`). A single physical `Photo` row can therefore legitimately sit in two albums whose `sorting_photos_col`/`photo_timeline` effective settings differ — a plain `photos.bucket_id` column would silently return the wrong value in one of those two contexts. This feature therefore places `bucket_id` on the **`photo_album` pivot row** instead (one value per photo-in-this-specific-album edge), not on `photos` — the correct generalization of Feature 061's "bucket_id is an edge property of the parent-child relationship" design to a many-to-many edge.

`ColumnSortingPhotoType` (`OWNER_ID`, `CREATED_AT`, `TITLE`, `TAKEN_AT`, `IS_HIGHLIGHTED`, `TYPE`, `RATING_AVG`) excludes `OWNER_ID` from bucketing, mirroring Feature 061's own treatment of albums' `OWNER_ID` — **per explicit user direction**, not because photos structurally guarantee single ownership the way sub-albums do (a shared regular `Album` can genuinely contain photos from several contributors). Ownership divergence within one listing is most pronounced for `TagAlbum`/`PersonAlbum` "matching photos" results (out of scope for this feature entirely, NG3) — for the regular-`Album` scope this feature actually covers, owner-based grouping is not treated as a valid/useful bucket dimension. The remaining 6 columns are bucketable (see FR-064-02).

Affected modules: application (new service, 2 new jobs, 1 new console command, 1 new migration on `photo_album`), REST (3 new routes, 1 controller, 3 actions, 3 requests, 3 resources), no core/CLI-beyond-the-one-command/UI changes. **Backend-contract-only** — no v8 frontend consumer, mirroring Feature 061's own precedent (a follow-up adoption feature, mirroring Feature 063, is required before any v2 photo-listing path could be retired).

## Goals

- **G1:** Add a nullable `bucket_id` column (+ composite index) to the **`photo_album` pivot table** (not `photos`), so a photo's bucket is correctly scoped per album it belongs to.
- **G2:** Provide `GET /Albums/{album_id}/Photos/buckets` — indexed `GROUP BY photo_album.bucket_id` counts + read-time labels for an album's direct photos, gated by `modules.is_struct_of_array_enabled` (no new flag).
- **G3:** Provide `GET /Albums/{album_id}/Photos` — whole-album-at-once SoA render data (see FR-064-07 for the exact field list — `ids`/`bucket_ids`/`ratios`/`owner_ids`/`is_highlighteds`/`is_validateds`/`is_videos`/`is_raws`/`is_live_photos`/dates unconditionally, plus config-gated rating/overlay-text/tags), zero pagination, mirroring Feature 057/061's "never paginate" precedent (justified by the SoA payload-size math already in `virtual-scrolling-study.md`).
- **G4:** Provide `GET /Albums/{album_id}/Photos/details` — the information needed when a user is about to open a photo (description, tags, rating, EXIF-lite, watermark-aware size-variant URLs — see FR-064-10/FR-064-19), explicitly scoped (never whole-album) to either one `bucket_id` or an explicit, capped `photo_ids[]` list, so its heavier payload never grows unbounded with album size.
- **G5:** Make 6 of `ColumnSortingPhotoType`'s 7 values bucketable, with a well-defined bucket-key derivation per column (date truncation, alphabetical/date-prefix title, boolean, enum value, or rounded rating). `OWNER_ID` is excluded from bucketing entirely, per explicit user direction (mirrors Feature 061's album `OWNER_ID` exclusion) — see Non-Goals.
- **G6:** Add two new, **photo-specific** instance-wide configs — `photo_title_bucket_mode` (`date_prefix`\|`alphabetical`, default `date_prefix`) and `photo_title_bucket_prefix_length` (int ≥ 1, default 1) — governing `TITLE`-sorted photo bucketing. Per explicit user direction, Feature 061's `title_bucket_mode`/`title_bucket_prefix_length` are **album-only** and must not be reused or shared for photos, even though the mechanism is otherwise identical.
- **G7:** Keep every tier's photo-visibility curation byte-for-byte consistent with what `PhotoRepository::getPhotosForAlbumPaginated()` already enforces today — non-admins never see another user's unvalidated (pending-moderation) uploads, in listings **or** bucket counts.
- **G8:** Reuse `ManagedCacheService`/`CacheKeyProvider` for all three tiers, invalidated by the same photo-mutation events (`PhotoSaved`, `PhotoMoved`, `PhotoDeleted`, `AlbumSaved`) already dispatched by existing write paths (`MoveOrDuplicate::do()`, upload pipes) — zero or minimal new dispatch call sites.

## Non-Goals

- **NG1:** No frontend adoption in this feature — mirrors Feature 061's own precedent exactly. A separate follow-up feature (mirroring how Feature 063 adopted Feature 061) wires a virtualized, justified-row-packing photo grid to these three endpoints.
- **NG2:** No change to `AlbumPhotosController`/`GetAlbumPhotosRequest`/`PhotoRepository::getPhotosForAlbumPaginated()`/`PaginatedPhotosResource` — v2 stays byte-identical, coexists unchanged.
- **NG3:** No `TagAlbum`/`PersonAlbum`/`BaseSmartAlbum` support in this feature — `{album_id}` must resolve to a regular `Album`; the other three types 404. Mirrors Feature 061's original scope (matching-album support was itself a same-day follow-up there, and can be revisited for photos the same way if requested).
- **NG4:** No recursive photos (`HasManyPhotosRecursively`) — only photos **directly** linked to `album_id` via `photo_album` (`HasManyChildPhotos`'s scope), matching the sub-album tier's "direct children only" philosophy.
- **NG5:** *(Revised twice per explicit user direction — see FR-064-19/20/21)* `details` **is** meant to carry the information needed when a user is about to open a photo — it is not merely a "hover card" tier, superseding this Non-Goal's original framing. **Resolved (Q-064-06):** `ratios`+`details` combined are meant to fully reconstruct v2's `PhotoResource`, including `palette`, `statistics`, `checksum`/`original_checksum`, and size-variant URLs (all now in scope — FR-064-19/20/21) — the only exception is `next_photo_id`/`previous_photo_id`, which stay unreconstructed because v2's own `PhotoResource` always sets both to `null` in this exact album-listing context anyway (nothing real to reconstruct). Whether a future frontend feature actually retires the lightbox's current "read the already-loaded heavy `PhotoResource` from the grid" pattern (`PhotoState.ts:55`) in favor of calling `ratios`+`details` remains out of scope for *this* backend-contract-only feature (NG1) regardless of how complete the field set becomes.
- **NG6:** No thumbnail/pixel resolution — resolving a size-variant **URL** to actual image bytes is still always the existing Feature 056 `GET /Asset/{album_id}/{photo_id}/{size_variant}` endpoint's job, unchanged. `buckets` and `ratios` return photo **ids** only, exactly like Feature 061's `cover_id`. `details` is the one exception (FR-064-19, per explicit user direction): it returns resolved size-variant **URLs**, not just ids — but even there, this feature never generates or applies a watermark itself; it only surfaces the URL/`is_watermarked` state the existing `WatermarkerJob`/`SizeVariant` pipeline already produced at write time.
- **NG7:** No new feature flag — reuses `modules.is_struct_of_array_enabled` (Feature 058's flag) exactly as Feature 061/062 do.
- **NG8:** No tag-filter/person-filter query parameters on any of the three tiers (unlike v2's `tag_ids`/`tag_logic`/`person_id`) — this feature covers the base "all direct photos" listing only; filtered variants are left for a future amendment if requested, mirroring how Feature 057 deferred a `search` parameter.
- **NG9:** No per-photo `can_edit`/`can_download`/`can_delete` boolean grants tier, and no dedicated fourth `/rights` endpoint (unlike Feature 061's separate `/rights` endpoint for albums) — **resolved, confirmed by user (Q-064-02, Option A)**. Per FR-064-11, `owner_id` (in `ratios` and `details`) is the only rights-adjacent field this feature exposes — every other right a photo context menu needs is already uniform across an album's photos and already available to the client via the album's own existing rights object; only ownership genuinely varies photo-by-photo (relevant today for the owner-only rating rule, Feature 059's Q-059-01 resolution).
- **NG10:** No change to `nsfw_status`'s existing per-photo AI-detection semantics — this feature reads it for `details` display only, never as an additional visibility filter (photo-level NSFW moderation is a separate, already-existing pipeline, not a listing-visibility concern here).
- **NG11:** No `OWNER_ID` bucketing for photos. Per explicit user direction, ownership is **not** considered a valid bucketable dimension for a regular `Album`'s direct photos, even though (unlike sub-albums) individual photos within one shared album can genuinely have different owners from each other and from the album's own owner. `OWNER_ID`-sorted albums always report `bucketable: false` (FR-064-05) and `bucket_id` is never computed for them (FR-064-02) — mirrors Feature 061's album `OWNER_ID` treatment exactly, but here by policy rather than by structural single-valuedness.

## Appendix

### Resolved decisions

**`bucket_id` storage: `photo_album` pivot row, not `photos` column.** A naive port of Feature 061 would add `bucket_id` directly to `photos`, mirroring `albums.bucket_id`. This is incorrect: `photo_album` is a genuine many-to-many pivot (composite PK `(photo_id, album_id)`), and `MoveOrDuplicate::do()` explicitly supports linking one physical `Photo` into a second album without removing its first link (the "copy" case). A single photo's correct bucket value under Album A's sort settings can differ from its correct value under Album B's — a `photos.bucket_id` column has no way to hold both. Placing `bucket_id` on the pivot row is the direct generalization of Feature 061's own design principle (`bucket_id` is a property of the parent-child *edge*, computed from the parent's settings) to a many-to-many edge. See NFR-064-06 for the regression test this decision demands.

**`OWNER_ID` is excluded from photo bucketing, per explicit user direction (NG11).** An earlier draft of this spec made `OWNER_ID` bucketable for photos, reasoning that (unlike sub-albums, which always share their parent's exact owner) a shared regular `Album` can genuinely contain photos from several different contributors, so grouping by owner is technically meaningful. The user rejected this: ownership divergence is not treated as a valid/useful bucket dimension for photos, and the case where it would matter most (a `TagAlbum`/`PersonAlbum` "matching photos" listing spanning many owners) is out of scope for this feature entirely (NG3) regardless. `OWNER_ID`-sorted albums now get the exact same treatment Feature 061 gives `OWNER_ID`-sorted albums: `bucketable: false`, `bucket_id` never computed, no `GROUP BY` ever executed — the difference is this is now a deliberate policy choice for photos, not a structural single-valuedness argument.

**The other 6 `ColumnSortingPhotoType` values are bucketable.** `RATING_AVG` (a continuous, nullable `decimal(5,4)`) is made bucketable by rounding to the nearest integer star (`"1"`..`"5"` — `"0"` is unreachable, since every individual rating is constrained to 1–5 so a real average can never round to 0 — plus `"unknown"` for a `null`/never-rated photo) rather than excluded outright — a small, well-defined, bounded (≤6-way) grouping, unlike the truly-unbounded raw value.

**Photo `TITLE` bucketing gets its own, separate config pair (G6), not a reuse of Feature 061's album config.** An earlier draft of this spec proposed reusing Feature 061's `title_bucket_mode`/`title_bucket_prefix_length` for photo `TITLE` bucketing too, reasoning that one shared "how do we alphabetically/date-bucket by title" setting would avoid a second, functionally-identical config pair. The user rejected this explicitly: those two configs are **album-only**. Feature 064 instead introduces `photo_title_bucket_mode`/`photo_title_bucket_prefix_length` (same two values/defaults, same semantics, `PhotoBucketComputer`-local) as genuinely independent settings — an admin can configure album and photo title-bucketing differently, and changing one never affects the other.

**Tier 3 (`details`) is deliberately not whole-album — confirmed, with asymmetric caps (Q-064-01/Q-064-04, user 2026-09-05).** Unlike `buckets`/`ratios` (both cheap enough, per the `virtual-scrolling-study.md`'s own SoA payload-size math, to stay unpaginated even at five-figure photo counts), `details`' per-photo payload is heavy — more so now that it also reconstructs full `PhotoResource` parity (Q-064-06) — so an unbounded whole-album response would reopen the exact problem this feature exists to avoid. The user's own framing — "details for the current album/bucket" — already pointed at bucket-scoping; this spec adds an explicit-id-list alternative (FR-064-09) so a client is never blocked by the non-existence of a suitable bucket boundary for its current viewport. The two modes ended up with deliberately **different** cap behavior, not a symmetric one: `bucket_id` mode is uncapped (returns every photo in the bucket, however many — the client is expected to consult `buckets`' own `counts[]` before choosing this mode for a potentially-huge bucket); `photo_ids[]` mode is capped at 300 ids as input, 422 above, since that mode's request shape is entirely client-controlled and has no natural size ceiling of its own.

**`ratios`+`details` combined must fully reconstruct `PhotoResource` — confirmed (Q-064-06, user 2026-09-05).** `palette`, `statistics`, `checksum`/`original_checksum`, `updated_at`, live-photo fields, `face_count`, and all 9 size-variant URLs are now all in scope (FR-064-19/20/21) — an earlier draft had deliberately excluded these as "lightbox-adjacent but not requested," which the user overrode directly. `statistics` surfaced a genuine correctness subtlety during this resolution: `PhotoPolicy::canReadMetrics()`'s `metrics_access=owner` mode is **per-photo**, not per-request (mirrors why `owner_id` itself needed to be per-photo elsewhere in this feature) — a `details` response spanning photos from two different owners can legitimately show `statistics: null` for one and real values for the other, in the same response, for the same caller. `next_photo_id`/`previous_photo_id` remain the one unreconstructed pair, but only because v2's own `PhotoResource` always nulls them in this exact listing context too — there is nothing real to reconstruct.

**Per-photo rights are folded into `ratios`/`details` as `owner_id` only, not a fourth `/rights` endpoint — confirmed (Q-064-02, Option A, user 2026-09-05).** Every photo-menu action except the owner-only rating rule is already sourced today from the containing album's single, uniform rights object; only ownership genuinely varies per photo. If a materially richer per-photo grant model is wanted later, a dedicated `/rights` tier (mirroring Feature 061's shape) remains a viable follow-up amendment.

**`ratios`' aspect-ratio SQL deliberately does not reproduce `getAspectRatioAttribute()`'s video-forces-1 special case — confirmed (Q-064-07, user 2026-09-05).** The Eloquent accessor returns `1` for a video lacking both a `MEDIUM` and `SMALL` size variant, even if an `ORIGINAL` row with a real, meaningful ratio exists. An earlier draft of FR-064-08 implicitly assumed the SQL `COALESCE` would produce identical results to that accessor "exactly" for every case; the user corrected this directly for the video branch: "we want to use the video aspect ratio also here and not just default to 1." The `COALESCE(sv_original.ratio, sv_medium.ratio, sv_small.ratio, 1)` stays exactly as originally drafted — it already does the right thing, the accessor's *own* video branch is the one being deliberately not mirrored, not the SQL. `1` is now reached only when none of the three size variants exist at all, for a photo or a video alike.
