## Overview

Feature 057 introduced the flat, `toBase()`-queried Struct-of-Arrays (SoA) response convention (ADR-0009). Feature 061 applied it — plus a `bucket_id`-driven virtual-scroll backend (buckets / children-data / rights) — to **one album's direct children**. The root gallery view (`GET /api/v2/Albums`, `App\Actions\Albums\Top::get()`) is the last major album-listing surface still fully Eloquent-hydrated across five categories (smart albums, tag albums, person albums, pinned albums, root albums split owned/shared) with no bucket/virtual-scroll backend at all.

This feature ports the SoA contract to root, split across **two structurally different endpoint families**, reflecting a real technical asymmetry:

1. **Root albums** (`parent_id IS NULL`) — get the full buckets/index/rights trio, exactly like sub-albums, **plus** a new `scope` dimension (`own` \| `shared`) that reproduces today's owned/shared partition. Root's ownership is heterogeneous (unlike a single album's children, which always share that album's exact owner), so `shared` scope groups by owner as its primary dimension — but this is a **live, read-time `GROUP BY owner_id`**, never the persisted `bucket_id` column (see Non-Goals). `own` scope behaves exactly like the existing sub-album tier: `bucket_id`-driven, date/title-based.
2. **Smart / person / tag / pinned albums** — flat, unbucketed SoA listings (these categories are curated/bounded by an admin's tag/person taxonomy or explicit pin action, not by photo volume, so no virtual-scroll backend is warranted — mirrors Feature 061's own precedent of excluding `TagAlbum`/`PersonAlbum` from bucket tiering). Person and pinned albums additionally get the same `own`\|`shared` scope as root (flat/ungrouped either way — no per-owner buckets, no `/buckets` route for either); smart and tag albums stay un-scoped. Tag albums additionally get a rights endpoint (they are user-editable/deletable objects with real per-row grants); smart, person, and pinned albums do not (smart albums are built-in/non-manageable; person albums are AI-generated; pinned albums are ordinary `Album` rows already covered by `/Albums/root/rights` when they're also root albums — a dedicated pinned-rights endpoint would be redundant).

A second, independent change closes a real, currently-silent gap this design work surfaced: `sorting_albums_col`/`album_sorting_col` currently accept `OWNER_ID` as a configurable value (`ColumnSortingAlbumType::OWNER_ID`), but a UI dropdown narrowing already shipped in Feature 060 quietly removed it from the *offered* choices (the `configs.type_range` for `sorting_albums_col` is already `created_at|title|max_taken_at|min_taken_at` — no `owner_id`) without ever removing it from the enum or migrating stray existing values. This feature finishes that removal: `OWNER_ID` is deleted from `ColumnSortingAlbumType` outright, with a migration rewriting any surviving `owner_id` value (instance config or per-album override) to `created_at`. The always-on ownership grouping (root's `shared` scope) is **not** this config — it is hardcoded root behaviour, independent of `sorting_albums_col`, exactly like `Top::queryRootAlbums()`'s existing hardcoded `OWNER_ID`-first sort is today. (Pinned albums have their own, separate `sorting_pinned_albums_col` config, which is `ColumnSortingType`-based, not `ColumnSortingAlbumType`-based — untouched by this removal, still allows `OWNER_ID` as a value, since `Top::queryPinnedAlbums()` never bucket-ifies it either.)

Third, per explicit direction, this feature also **consolidates** Feature 061's three single-action controllers into one, and organizes all album-listing v3 controllers under a new `Gallery\AlbumListing` namespace, so eight new routes (plus three renamed ones — Feature 061's sub-album tier drops its `/children` path segment, mirroring root's own naming, Q-062-12) cost roughly eight new files, not twenty-plus (see FR-062-12, NFR-062-09).

Affected modules: application (new job, enum removal + migration, `SettingsController` dispatch, controller/request/resource reorganization), REST (8 new routes, 3 existing routes both re-pointed to the consolidated controller **and** renamed — `/children` dropped). No core/CLI/UI changes. No change to `albums.bucket_id`'s existing computation semantics — it remains exclusively date/title-derived, system-wide, for both root (`own` scope) and sub-albums.

## Goals

- **G1:** Serve root albums (`parent_id IS NULL`) via the same buckets/index/rights trio as sub-albums, gated behind `features.struct-of-array`.
- **G2:** Add a `scope` (`own`\|`shared`) dimension to all three root endpoints, reproducing today's owned/shared partition; guests only ever see `shared` semantics (there is no unpartitioned third mode — a guest has no "own" albums by definition).
- **G3:** For `scope=shared`, group by owner as the primary dimension, then order by the instance's normal configured sort criterion within each owner group — via a **live `GROUP BY owner_id`** at read time, never via the persisted `bucket_id` column.
- **G4:** Never compute or store an owner-derived value into `albums.bucket_id`, anywhere, for any album (root or sub-album) — `bucket_id` stays exclusively date/title-derived.
- **G5:** Remove `OWNER_ID` as a selectable value of `sorting_albums_col`/`album_sorting_col` (delete `ColumnSortingAlbumType::OWNER_ID`), migrating any surviving `owner_id` value to `created_at`. The hardcoded owner-grouping behaviour for root's `shared` scope is unaffected by this removal — it was never sourced from this config.
- **G6:** Keep root `bucket_id` (`own` scope) live against instance-wide sorting/timeline/title-bucket config changes, closing the dispatch gap `RecomputeChildAlbumBucketsJob` deliberately doesn't cover (parent-scoped only).
- **G7:** Serve smart/person/tag/pinned albums as flat, unbucketed SoA listings, replacing `Top::get()`'s eager-loaded Eloquent collections for these four categories; tag albums additionally get a rights endpoint.
- **G8:** Consolidate the album-listing v3 controller surface (Feature 061's existing 3 files + this feature's new endpoints) into a small, clearly-categorized set of multi-action controllers under a new `Gallery\AlbumListing` namespace, reusing shared request/resource classes wherever the shape is structurally identical, so file count grows sub-linearly with route count.

## Non-Goals

- **NG1:** No `GET /api/v2/Albums` / `AlbumsController` / `Top` / `TopAlbumDTO` / `RootAlbumResource` change — v2 stays byte-identical.
- **NG2:** No v8 frontend adoption in this feature. A separate follow-up feature (mirroring how Feature 063 adopted Feature 061) wires the v8 root/landing view to these endpoints. This feature is backend-contract-only. *(2026-09-02 amendment: the `/Albums/smart` adoption specifically ended up folded into Feature 063 itself as an addendum, not a new feature number — per user direction to "expand Feature 063." This backend feature's own scope is unchanged by that choice; NG2 otherwise still holds for `/Albums/persons`/`/Albums/tags`/`/Albums/pinned`/`/Albums/root`, all still unadopted. See Feature 063 spec.md's 2026-09-02 addendum, Q-063-14.)*
- **NG3:** No bucket/virtual-scroll tier for the smart/person/tag/pinned-album *category listings themselves* — flat only (Overview, point 2). Pinned albums specifically are **never** bucketable, in either sense (own scope's date/title `bucket_id`, or shared scope's live owner grouping) — a pinned album's real position in the tree is arbitrary (it need not be a root album), so its `bucket_id` (governed by its *actual* parent's sort settings, per Feature 061) has no coherent shared meaning across a pinned list spanning different real parents; attempting to bucket it would mix incomparable bucket sizes/dimensions from unrelated parts of the tree.
- **NG4:** No rights endpoint for person, smart, or pinned albums in this feature (explicit scope decision — see Appendix). A pinned album that is also a root album already gets rights coverage via `/Albums/root/rights`; a pinned sub-album already gets it via the existing sub-album `/Albums/{album_id}/rights` tier (queried against its real parent) — a dedicated pinned-rights endpoint would be redundant either way.
- **NG5:** No compound/nested bucket key (owner × date) anywhere — `shared` scope's owner grouping and `own` scope's date/title bucketing are two independent, single-level mechanisms, never combined into one.
- **NG6:** No change to `deduplicate_pinned_albums` semantics — reused as-is.
- **NG7:** `ColumnSortingType::OWNER_ID` (the broader, internal enum — distinct from `ColumnSortingAlbumType`) is **not** removed; it stays available for the internal, non-configurable ordering `Top::queryRootAlbums()`/this feature's `shared`-scope query already need to express "order by owner" in SQL. Only the *configurable* `ColumnSortingAlbumType::OWNER_ID` is removed (G5).
- **NG8:** No new database migration beyond the one enum-removal config/data rewrite (FR-062-08) — `albums.bucket_id` and its `(parent_id, bucket_id)` index already exist from Feature 061 and need no schema change.
- **NG9:** Neither `/Albums/pinned`'s nor `/Albums/persons`'s `shared` scope groups by owner the way root's `shared` scope does (NG5's "never combined" applies here too, but this is the stronger case — their shared sets aren't grouped by *anything* server-side, not even a single-level owner grouping) — each is one flat, ungrouped list (FR-062-15). Neither gets a `/buckets` route either.

Cache keys extend the existing `pinnedAlbumsListingKey(...)`/`personAlbumsListingKey(...)` with the `scope` dimension; tags stay `pinnedAlbumsListingTag()`/`personAlbumsListingTag()`. | `own`/`shared` split matches root's semantics exactly for validation; result is flat either way, for both categories. | Reuses `GetScopedAlbumsRequest` (FR-062-02) — no separate validation logic. | Missing/invalid `scope` for authenticated, or `scope=own` for guest → 422 (identical to root), for both routes. | None. | Q-062-10, Q-062-13 (resolved). |
| FR-062-16 *(2026-09-02 amendment, Q-063-15)* | `AlbumCategoryController::smart()` gains a batched cover-photo lookup instead of always reporting `cover_ids: null`: `AlbumUserThumb::query()->whereIn('album_id', $ids)->where('user_id', '=', Auth::id())->pluck('photo_id', 'album_id')` — one indexed query (not per-row, not a live `photos` query, so the endpoint's "zero-`photos`-query" design goal (Overview/original `smart()` docblock) still holds, only widened from "zero SQL queries" to "zero *photo* queries"), reading the same `album_user_thumbs` cache `BaseSmartAlbum::getThumbAttribute()`/`RecomputeAlbumUserThumbsJob` (`KIND_SMART`) already read from and keep warm for the v2 `Top::get()` path. `cover_ids[i]` is the cached `photo_id` on a hit, `null` on a miss (never resolved live) — a miss self-heals the next time anything triggers a live resolution for that (album, viewer) pair elsewhere (e.g. a v2 root-page load), exactly like every other `AlbumUserThumb` cache miss today. | A viewer who has previously triggered a live thumb resolution for a given smart album (v2 root load, or any other `getCachedOrLiveThumb()` call site) sees that same real cover photo through `/Albums/smart` too, not a regression to no-cover. | N/A. | Cache miss (never-viewed-by-this-viewer smart album) → `cover_ids[i]` stays `null`, same as today's pre-amendment behavior — not a new failure mode, just the pre-existing one narrowed to only the not-yet-cached case. | None. | Q-063-15 (Feature 063 addendum); `App\Models\Extensions\CachesAlbumUserThumb`; `App\Jobs\RecomputeAlbumUserThumbsJob::KIND_SMART`. |

## Appendix

### Resolved decisions

**Q-062-01 · Guest privacy when the effective root sort column is `OWNER_ID`**
Superseded twice over. First by G5/FR-062-08: `OWNER_ID` is no longer a possible `sorting_albums_col` value at all, system-wide, so the *configured-column* framing this question originally raised no longer has a code path to occur through. A same-day follow-up then reasoned that, since `shared` scope's owner-grouping is now unconditional rather than config-dependent, there was "nothing left to hide" and let guests see real owner-name labels — that reasoning was itself reconsidered and reversed by explicit user direction; see Q-062-14 for the final, opposite resolution (guests never see real names; `users` join skipped entirely for unauthenticated callers). Do not read this entry as current guidance on guest label exposure — Q-062-14 is authoritative.

**Q-062-02 · `scope` shape — required own/shared vs. optional combined list**
Resolved — required `own`/`shared` for authenticated callers; guest defaults to (and is limited to) `shared`. See FR-062-02.

**Q-062-03 · Route shape for a parent-less "children" concept**
Resolved — literal path segments (`root`, `smart`, `persons`, `tags`), registered ahead of `/Albums/{album_id}/...`. Dropped the earlier "children" suffix for root (`/Albums/root/children`) in favor of `/Albums/root` directly — root is not conceptually "children of a virtual parent album," it is its own top-level listing (closer to Feature 057's `/Albums` in spirit, just bucketed/scoped).

**Q-062-04 · Tag/person/pinned categories — one combined endpoint or separate**
Superseded by this revision's explicit direction: **separate** routes per category (`/Albums/smart`, `/Albums/persons`, `/Albums/tags`, `/Albums/pinned`), not one combined `Albums::rootCategories` endpoint as originally drafted. See Q-062-09 for `pinned` specifically, which was briefly dropped and then reinstated.

**Q-062-05 · Should a guest ever be allowed to request `scope=own`?**
Resolved — no, 422. Silently returning an empty result would hide a client bug; rejecting is more honest and matches how `GetScopedAlbumsRequest`'s validation already has to distinguish authenticated-vs-guest for the `scope=shared`-default behaviour anyway.

**Q-062-06 · How does `shared`-scope owner-grouping coexist with "we do not want to bucket by `owner_id`"?**
Resolved — two independent mechanisms, never conflated: the *persisted* `bucket_id` column (written by `AlbumBucketComputer`, backfilled/kept-live by the recompute jobs) stays exclusively date/title-derived, forever, for every album (root `own` scope included) — this is what "we do not want to bucket by owner_id" rules out. `shared` scope's owner-grouping is a **separate, live, read-time** `GROUP BY owner_id` query that never touches `AlbumBucketComputer` or the `bucket_id` column at all; the *response's* `bucket_id` field is repurposed to carry `owner_id` for that scope only, purely so the client-side "group children rows by their `bucket_id` field" contract stays uniform across scopes without requiring two different client code paths.

**Q-062-07 · Should `ColumnSortingType::OWNER_ID` (the broader enum) also be removed?**
Resolved — no (NG7). Only `ColumnSortingAlbumType::OWNER_ID` (the *configurable* album-sort-column value) is removed. `ColumnSortingType::OWNER_ID` remains available for internal, non-configurable SQL ordering (`Top::queryRootAlbums()`'s existing hardcoded sort, and this feature's own `shared`-scope `ORDER BY owner_id` construction) — removing it would break code that has nothing to do with the admin-facing config surface this feature is narrowing.

**Q-062-08 · Remove `OWNER_ID` as a selectable `sorting_albums_col`/`album_sorting_col` value entirely, or keep supporting it (with owner-aware bucketing, as an earlier draft of this spec proposed)?**
Resolved — remove, per explicit user direction. `configs.type_range` for `sorting_albums_col` already excludes `owner_id` since Feature 060's dropdown narrowing, so this closes a dead config path rather than building new owner-aware machinery into `AlbumBucketComputer` (which an earlier draft of this spec had proposed and which is now explicitly rejected — see Q-062-06). Migrate surviving `owner_id` values to `created_at`. See FR-062-08, G5.

**Q-062-09 · `pinned` albums — dropped from scope (Q-062-04) or reinstated?**
Resolved — reinstated, as a fifth flat category endpoint (`GET /Albums/pinned`), per explicit user follow-up ("Oh good point, I forgot about the pinned albums. Add it back."). No rights endpoint (NG4 — redundant with `/Albums/root/rights` for a pinned root album, or the existing sub-album rights tier for a pinned sub-album). Keeps its own separate `sorting_pinned_albums_col` config untouched by the `OWNER_ID` removal (that config is `ColumnSortingType`-based, not `ColumnSortingAlbumType`-based) and its existing not-restricted-to-root scope, matching `Top::queryPinnedAlbums()` exactly. See FR-062-09; see also Q-062-10/Q-062-11 for the further own/shared refinement added in a second follow-up.

**Q-062-10 · Should `/Albums/pinned` also get an own/shared split, and how should `shared` be structured?**
Resolved — yes, own/shared split reusing root's exact `GetScopedAlbumsRequest`/validation (FR-062-02/FR-062-15), per explicit user follow-up. Unlike root's `shared` scope, pinned's `shared` is **one flat, ungrouped list** — "in the later case, they are all grouped" (user's own words) was interpreted as "lumped into one undifferentiated set," not "grouped by owner," given the immediately-following instruction that pinned must never be bucketable at all (Q-062-11) — a per-owner grouping would itself be a form of bucketing this feature explicitly rules out for pinned. A guest's result is exactly what `applyVisibilityFilter()` already lets through today (i.e., genuinely public pinned albums) — no new filtering logic.

**Q-062-11 · Why is `/Albums/pinned` never bucketable, in either the date/title or the owner-grouping sense?**
Resolved — per explicit user direction: a pinned album's real tree position is arbitrary (it need not be root), so its persisted `bucket_id` is governed by whatever its *actual* parent's sort settings are (Feature 061's mechanism) — mixing `bucket_id` values computed under unrelated parents into one "pinned" bucket list would be semantically incoherent (different, incomparable dimensions masquerading as one). The user's own framing: "this should solve the potential conflict between the bucket sizes as pinned albums are possibly not as root." Resolved by simply never exposing a buckets endpoint for `/Albums/pinned` at all (NG3/NG9) — no compound/normalized bucket key was considered necessary to invent.

**Q-062-12 · Should Feature 061's already-shipped `/Albums/{album_id}/children[/buckets\|/rights]` paths be renamed to drop `/children` (`/Albums/{album_id}[/buckets\|/rights]`), matching root's naming?**
Resolved — yes, per explicit user proposal ("That would make more sense no?"). Safe to do despite Feature 061 already being shipped/completed, because it was explicitly built with **no v8 frontend consumer yet** (confirmed in the roadmap's own Feature 061 entry) — there is nothing external depending on the old path today. The rename is path-only; query logic and response shape are untouched (FR-062-01/FR-062-12). The one real cost: Feature 061's existing test files need their request-URL literals updated (mechanical, one line per test method) — this is *not* a violation of "pure refactor," since the thing being verified (the assertions) stays byte-for-byte identical; only the string naming which endpoint to hit changes (NFR-062-06 reworded accordingly).

**Q-062-13 · Should `/Albums/persons` also get the own/shared split, given `PersonAlbum` rows carry a real `owner_id` (confirmed via `BaseAlbumImpl`, mirrors `TagAlbum`)?**
Resolved — yes, per explicit user proposal, reusing the exact same `GetScopedAlbumsRequest`/flat-`shared`/no-buckets pattern already established for `/Albums/pinned` (Q-062-10/Q-062-11) — one shared request class now covers 5 methods across `AlbumRootController` and `AlbumCategoryController::persons()`/`pinned()`. `/Albums/tags` and `/Albums/smart` deliberately stay un-scoped — the user's list included `scope` for persons but not tags, and tag albums/smart albums were not asked to gain it; if that need arises later, FR-062-09 documents it as a revisit point.

**Q-062-14 · Should unauthenticated guests receive real owner display names via `/Albums/root/buckets`'s `shared`-scope labels?**
Resolved — no. The `users` join and label resolution run only for authenticated callers. A guest's `shared`-scope buckets still group by the real `owner_id` (accurate counts, accurate bucket count) but every label is hardcoded to `"unknown"`, and the `users` join is never executed for a guest request at all — not merely hidden after the fact. This reverses an earlier same-day resolution (originally captured, then superseded, in Q-062-01) that had guests seeing real names; that earlier call was made unilaterally during a fast pivot and is now corrected by explicit user direction. See FR-062-05, NFR-062-02, S-062-29.

**Q-062-15 · Does `bucketable:false` mean "structurally ungroupable" or "zero results this time"?**
Resolved — it keeps Feature 061's exact meaning: `bucketable` describes whether the grouping mechanism is available, not whether there happens to be data. `shared`-scope buckets are unconditionally `bucketable:true` for every caller (guest included); a zero-result `shared` query returns `bucketable:true` with empty arrays, exactly like 061's own empty-children behaviour, never `bucketable:false`. The earlier "`bucketable:false` only for an empty result" wording in a same-day draft is corrected. See FR-062-05, S-062-07.

**Q-062-16 · Is `/Albums/root/rights`'s `owner_id` null for `scope=own`, or only for `scope=shared`?**
Resolved — null unconditionally, both scopes (root has no single "parent album" whose grants the endpoint is checking, regardless of whether the row set happens to share one real owner under `own` scope). Refined per follow-up ("if it is always null do we need it?"): since the value is *always* null for root, the `owner_id` key is omitted from the JSON payload entirely for root's rights response (a conditional resource field), rather than serialized as a useless `null`. The sub-album and `TagAlbum`/`PersonAlbum`-matching tiers, where the value is always real, are unaffected — same shared resource class, the key simply isn't null there. See FR-062-06, DO-062-04, S-062-08/09.

**Q-062-17 · Does dropping `/children` make `/Albums/{album_id}` read as "fetch one album" rather than "list its children"?**
Resolved — reconsidered and kept as originally specced (Q-062-12 stands). `/Albums/{album_id}`, `/Albums/{album_id}/buckets`, `/Albums/{album_id}/rights` proceed unchanged; the naming tradeoff (a singular-looking path returning a children collection) is accepted knowingly rather than reverted to the `/children`-suffixed form.
