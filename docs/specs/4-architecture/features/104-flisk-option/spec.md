## Overview
Self-hosters start Lychee with `docker-compose.yaml`. This feature adds an **optional** second way to start the same stack with [Flisk](https://flisk.sh), a local dev/self-host launcher: one `service.json` per Compose service under `services/lychee/`, plus a Compose file generated from them in `.autogenerated/docker-compose.yml`. No PHP, frontend, API, artisan or image change; `docker-compose.yaml` stays the documented main path and is not edited. Disclosure: the author works on Flisk.

## Goals
- G-104-01: `flisk up lychee` starts the same services as `docker compose -f docker-compose.yaml up` (lychee_api, lychee_worker, lychee_db, lychee_facial_recognition; phpmyadmin, nsfw and geo-decoding behind their profiles).
- G-104-02: An existing Compose install switches to the Flisk setup **without copying data**: same Docker volume names (`lychee_prod_mysql`, `lychee_ai_vision_embeddings`, `lychee_nsfw_queue`) and the same `./lychee/*` bind mounts: the generated file writes them as `../lychee/*` (relative to `.autogenerated/`, where Compose resolves them), and `docker compose config` resolves them to `<repo>/lychee/*`.
- G-104-03: Other services keep reaching each other by the Compose names (`lychee_api`, `lychee_db`), which are written as network aliases.
- G-104-04: `.autogenerated/docker-compose.yml` runs with plain Docker Compose and no Flisk (`docker compose --env-file .env -f .autogenerated/docker-compose.yml up -d`).
- G-104-05: Documentation in `docs/FLISK.md`, one pointer line in README, and a CI check that the generated file matches the `service.json` files.

## Non-Goals
- N-104-01: Replacing or editing `docker-compose.yaml`, `docker-compose.minimal.yaml`, the Dockerfiles or any image.
- N-104-02: Any change to application code, tests, API or UI.
- N-104-03: Production deployment or Kubernetes; Flisk does not deploy.
- N-104-04: Fixing the health checks of the optional nsfw and geo-decoding images, or the installer banner (all exist with `docker-compose.yaml`). The facial-recognition check is changed on the Flisk side only (FR-104-10), because `flisk up --wait` fails on it.

## Known `flisk up` requirements (found on Flisk 1.4.28, re-checked on 1.4.29 and 1.4.30)
Running the generated stack under `flisk up` (not only as plain Compose) needed three things that the plain Compose path does not on Flisk 1.4.28 (flisk-sh/flisk#1519, #2991, #2992). Flisk 1.4.29 (flisk-sh/flisk#3001) fixes two of them and Flisk 1.4.30 (flisk-sh/flisk#3010) the third. Re-checked from a fresh clone with the pinned `flisk-import` 0.16.0 and `@flisk-sh/flisk-export` 0.9.0 on Linux amd64 with Flisk 1.4.31 (an earlier macOS check on Flisk 1.4.30 used `flisk-import` 0.17.1 and found the same):

| ID | Requirement | Status on Flisk 1.4.29, and older versions |
|----|-------------|--------------------------------------------|
| FR-104-06 | `.flisk/project.json` `project.name` is lowercase (`lychee`). | **Fixed in Flisk 1.4.29, no workaround needed**: Flisk lowercases the name itself and `flisk-import` 0.17.0 and later writes it lowercase. Older Flisk (1.4.28 and earlier) refuses an uppercase name (folder `Lychee`): keep it lowercase by hand. |
| FR-104-07 | `lychee-api` and `lychee-worker` set `"DATABASE_URL": ""` in `env`. | **Fixed in Flisk 1.4.30, no workaround needed** (flisk-sh/flisk#3010; checked from a fresh clone: no `DATABASE_URL` or `TILT_DATABASE_URL` in the api container, API and worker healthy). Older versions: set `DATABASE_URL` to an empty string on both. On 1.4.29 it is still required: discovery fills in a `databaseName` and 1.4.29 treats it as asking for the shared Postgres. Lychee reads `DATABASE_URL` before `DB_*`. |
| FR-104-08 | `lychee-facial-recognition` sets `container.memory: "4G"`. | **Fixed in Flisk 1.4.29, no workaround needed**: a service without `container.memory` gets no limit (memory limit 0, not OOM-killed; same for `lychee-geo-decoding` and `lychee-nsfw-classification`). Older Flisk (1.4.28 and earlier) applies a 512M default and OOM-kills the image: set `container.memory: "4G"` there, and `"2G"` on `lychee-geo-decoding` when its profile is used. |
| FR-104-10 | `lychee-facial-recognition` `healthCheck.command` uses the image's own Python: `["python3", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health', timeout=5)"]`. | **Needed on every Flisk version**: the image has no `curl`, so the check copied from `docker-compose.yaml` keeps it unhealthy and `flisk up lychee --wait` exits 1. Checked on Linux amd64 (GitHub `ubuntu-latest`, Flisk 1.4.30): the Python call returns 200 inside the container. `docker-compose.yaml` is not changed. |
| FR-104-09 | `.gitignore` covers what `flisk up` writes: `/.tiltignore`, `/shared-platform-engineering/`, `/services/platform/`, `/services/**/.autogenerated/`, `/.flisk/.flisk-out/`. | Unchanged: these Flisk runtime outputs must not be committed. The committed generated files are only those of FR-104-04 (`services/`, `.flisk/project.json`, `.autogenerated/docker-compose.yml`). |

Known behaviour that is **not** caused by the Flisk setup: the `lychee_facial_recognition` image has no `curl`, but its health check calls it, so it reports unhealthy under `docker-compose.yaml` too while `/health` answers 200 (the Flisk setup uses FR-104-10 instead; `docker-compose.yaml` is not changed). The `lychee_nsfw_classification` image (no `curl`) and the `lychee_geo_decoding` image (no `wget`, no shell) behave the same way under `docker-compose.yaml`. The installer page shows an empty "Please fix the errors" banner in both setups.

## Test Strategy
- **Models / Actions, REST API, Artisan, Frontend:** not affected (N-104-02).
- **Docs/Contracts:** CI job from FR-104-04; manual switch test S-104-03 recorded in the PR with screenshots and logs.

Already verified on a scratch machine (macOS, Docker 29.5.2, flisk-import 0.14.0 / flisk-export 0.7.0; re-checked with 0.15.0 / 0.8.0): S-104-02 and S-104-03 pass (API healthy in 12 s on the original install's volumes, a marker row written by the original stack is read back, `lychee_api` resolves), and the installer page is identical to the one served by `docker-compose.yaml`.

## Pinned versions
The fields this relies on (`container.networkAliases`, `healthCheck.startPeriod`, `volumes[].name`, `profiles`, `envFile`, `container.tmpfs`) are in Flisk CLI **1.4.27** (released 2026-11-01). The files are produced and checked with fixed versions:

| Step | Command |
|------|---------|
| Import | `FLISK_IMPORT_PACKAGE=flisk-import@0.16.0 flisk import . --yes` |
| Export | `npx @flisk-sh/flisk-export@0.9.0 compose . --force` |
| CI drift check | re-import + export in a scratch copy, then `git diff --exit-code`; plus the normalised `docker compose config` comparison (FR-104-04) |
| Start | `flisk up lychee --wait` (Flisk ≥ 1.4.31, checked on Linux amd64; 1.4.27 … 1.4.29 need the FR-104-06 … 08 workarounds) |

`flisk export compose` is the same exporter run through the Flisk CLI; the spec uses the pinned `npx` form everywhere so CI does not depend on the installed CLI.
