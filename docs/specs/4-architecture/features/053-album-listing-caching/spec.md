## Overview

Several queries dominate normal browsing of a Lychee instance and are re-executed, unmemoized, on every page view: `App\Repositories\AlbumRepository::getChildrenPaginated()` (the paginated list of an album's direct sub-albums, `app/Repositories/AlbumRepository.php:43-66`, served by `AlbumChildrenController`) and the four independent Eloquent queries inside `App\Actions\Albums\Top::get()` (the root gallery view, `app/Actions/Albums/Top.php`, served by `AlbumsController`) — one each for tag albums, person albums, pinned albums, and root/shared albums; a fifth piece of `Top()`'s output, the built-in smart-album list, involves no SQL query at all (it's a `Gate::check()`-filtered, config-driven in-memory list) and is not a caching concern. Each of these queries applies a permission-dependent visibility filter (`AlbumQueryPolicy::applyVisibilityFilter()`) and a configurable sort, and each is exactly the kind of expensive-but-memoizable computation `App\Services\Cache\ManagedCacheService` (Feature 052) was built for.

**This feature caches individual SQL queries, never a whole action's assembled output.** `Top::get()` bundles four independent queries into one `TopAlbumDTO`, but that bundling is presentational, not a caching boundary — each of the four is cached on its own (FR-053-02), and `TopAlbumDTO` is assembled fresh on every call from whichever pieces are cache hits or misses. The same principle governs the Tag detail page (§G/FR-053-26): only its album query is cached, not the whole `GetTagWithPhotosAndAlbums::do()` result that also includes an independent photo query.

Feature 052 shipped only the generic caching primitive (`remember()`/`forgetTag()`/`addTags()`); the invalidation wiring and the two pilot consumers it originally targeted (`AlbumRepository::getChildrenPaginated()` and `PhotoRepository::getPhotosForAlbumPaginated()`) were designed, then explicitly reworked and never implemented (see `docs/specs/4-architecture/features/052-managed-cache-service/spec.md`'s "Superseded Design" appendix). This feature resumes that work for the album-listing half only (photo-listing caching is out of scope, see Non-Goals), but goes materially further than the superseded design: a full repository audit (below) found the superseded design's three known gaps (`Move`, `SharingController`, `UserGroupsManagementController`) are a small fraction of the real mutation surface. At least a dozen additional silent mutation paths were found — including the single most common album-edit endpoint (`AlbumController::updateAlbum()`), an admin bulk-edit action that mass-updates album rows with zero events, and several raw/bulk SQL paths (nested-set tree repair, mass ownership propagation, cross-album cover cleanup on photo delete) that cannot be observed via Eloquent model events at all, by construction.

Consistent with that finding, this feature's invalidation design is **entirely event-driven at explicit dispatch sites in application code**, never via Eloquent model observers (`static::saved()`, `::observe()`, etc.). Model-level observers cannot see mutations performed through the query builder (`Model::query()->update(...)`), raw `DB::table()` calls, pivot `attach()`/`detach()`, or the nested-set vendor package's internal bulk `_lft`/`_rgt` rewrites — all of which are used extensively in the codebase for exactly the operations this feature must invalidate on.

## Goals

1. Cache `AlbumRepository::getChildrenPaginated()` via `ManagedCacheService::remember()`, keyed by parent album id, requesting user, page, and sort criteria.
2. Cache each of `Actions\Albums\Top::get()`'s four constituent queries (tag albums, person albums, pinned albums, root/shared albums) **individually** via `ManagedCacheService::rememberIf()`, each keyed by requesting user and its own sort criteria (none paginated). `Top::get()` itself is never wrapped — it stays a plain assembler that calls into four independently-cached (or live) pieces and builds `TopAlbumDTO` from whatever it gets back, every time.
3. Cache `GetTagWithPhotosAndAlbums::getAccessibleAlbums()` — the album half of the Tag detail page (`GET /api/v2/Tag`) — via `ManagedCacheService::rememberIf()` (FR-053-26). This feature caches **at the SQL-query layer, not the request/response layer**: every cached unit across Goals 1–3 is one specific query-producing method or query fragment, wrapped individually — never a whole controller action, a whole multi-query action method, or a DTO-assembling method. The Tag detail page's *photo* query is a separate, independent caching decision and stays uncached here (see Non-Goals).
4. Close every silent-mutation gap found by the audit below by adding an explicit domain-event dispatch at each site, so the cache (and any future consumer of the same signal) can react correctly. Where a suitable event already exists (`AlbumSaved`, `AlbumDeleted`), reuse it; otherwise introduce a new, narrowly-scoped event.
5. Fix a pre-existing latent bug found during the audit: `SetProtectionPolicy::do(BaseAlbum $album, ...)` unconditionally calls `AlbumSaved::dispatch($album)`, but `AlbumSaved`'s constructor is typed `Album $album`. Since `SetProtectionPolicy` is also invoked for `TagAlbum`/`PersonAlbum` instances (via `AlbumController::updateProtectionPolicy()` → `updateProtectionPolicyBase()`), this throws a `TypeError` at runtime whenever a tag or person album's protection policy is changed. This must be fixed as part of wiring `TagAlbumSaved`/`PersonAlbumSaved` (FR-053-11) — the fix is required for this feature's own correctness (Top's tag/person album sections must be invalidated on protection changes) and is not optional scope creep.
6. Finally ship the `managed_cache_enabled`/`managed_cache_ttl` config-row migration and the `SettingsController` `'Mod Cache'` visibility exemption that Feature 052 left undone (its T-052-05/T-052-06) — this feature is the first to actually depend on the gate being operational outside of tests.
7. Provide a dedicated `managed_cache_albums_enabled` toggle so album-listing caching specifically (all three consumers above) can be turned off without touching the master `managed_cache_enabled` switch, which would also affect any other future `ManagedCacheService` consumer. Subordinate to the master switch — both must be on for album-listing caching to actually happen.
8. Cover every new dispatch site and the resulting cache eviction with tests proving: (a) the mutation is invisible to the DB without the fix (regression proof), and (b) the cache entry is evicted and recomputed after the mutation.

## Non-Goals

- **Photo-listing caching** (`PhotoRepository::getPhotosForAlbumPaginated()`, and — same principle — `GetTagWithPhotosAndAlbums::getAccessiblePhotos()`, the photo half of the Tag detail page) — deliberately deferred to a future feature (explicit product decision; the photo-tag/rating/highlight mutation event audit this would require is not done here). This feature caches at the query level (Goal 3), so the Tag detail page's album query (FR-053-26) and photo query are independent decisions — caching one does not imply caching the other, and the endpoint's controller/response as a whole is never wrapped.
- **Whole-request, whole-response, or whole-multi-query-action caching of any kind, anywhere in this feature.** Every cached unit in this feature is exactly one SQL query (or, where a query needs eager loads to construct one coherent result — `getChildrenPaginated()`'s `owner`/cover relations, `getAccessibleAlbums()`'s eventual resource-mapping needs — the minimal set of queries needed for that one result): `getChildrenPaginated()`, each of `Top::get()`'s four constituent queries individually (not `Top::get()` itself, which is never wrapped), and `GetTagWithPhotosAndAlbums::getAccessibleAlbums()` (not `GetTagWithPhotosAndAlbums::do()`, which also runs the independent, uncached photo query). The existing `RouteCacher` (below) is the only mechanism in this codebase that caches at the HTTP-response layer, and this feature does not touch it.
- **Precise per-descendant invalidation for subtree-wide ownership propagation.** `Album::fixOwnershipOfChildren()` (called from `Move`, `Merge`, `Transfer`) mass-updates `owner_id` for an entire subtree in one raw query; enumerating every descendant to tag-evict precisely would require walking the subtree on every such operation, defeating the purpose of caching. Instead, any operation that triggers `fixOwnershipOfChildren()` on an album that actually has descendants performs one coarse, instance-wide cache flush (FR-053-18). Deliberate accuracy/performance tradeoff, not an oversight.
- **Fine-grained tagging for global sort-config changes and smart-album protection changes.** These two triggers (§8/§C of the audit) have no natural per-album or per-listing tag to hook (a config value, or an admin-only policy toggle with no per-item id). They are folded into the coarse, instance-wide flush (FR-053-16/17). `is_pinned` is **not** in this bucket — see FR-053-22, which gives it precise (if slightly widened) tagging instead, since it's set through the same dispatch sites as any other album attribute (FR-053-04) and doesn't warrant the coarse flush.
- **A generic, admin-configurable per-part cache toggle system** (Feature 052's Goal 4, "let admins configure which computations are cached" — a dynamic mechanism covering an arbitrary, extensible set of future `ManagedCacheService` consumers). Still undesigned. This feature ships exactly one hardcoded, purpose-built toggle (`managed_cache_albums_enabled`, Goal 6/FR-053-25) covering its own three consumer actions (six independently-cached queries) — not a reusable per-part configuration framework. A future consumer would need its own dedicated toggle the same way, not a generic registry.
- **Replacing or extending the existing HTTP response cache** (`RouteCacher`/`RouteCacheManager`/`CacheTag`, Feature 040, governed by `cache_enabled`). Untouched.
- **NSFW-based query filtering.** Confirmed by the audit (§9): `is_nsfw` is not read by `AlbumQueryPolicy::applyVisibilityFilter()` — it is purely a displayed/blurred attribute on the listing row, not a row-inclusion filter, for `getChildrenPaginated()` or any of `Top()`'s four sub-queries. No new filtering logic is introduced; `is_nsfw` changes are handled like any other displayed-attribute change (via `AlbumSaved`/`BaseAlbumRemoved` etc.), not as a visibility concern.
- **Session-scoped password-unlock state** (`Unlock::do()`). Confirmed irrelevant: unlocking a password-protected album changes *reachability* (can this session enter the album), not *visibility* (does the album appear in a listing) — passworded albums remain listed either way. No cache-key dimension for unlock/session state is introduced.

### G. Tag detail page — album-query caching (third consumer, added post-review)

A third listing surfaced during spec review: the Tag detail page (`GET /api/v2/Tag` → `TagController::get()` → `App\Actions\Tag\GetTagWithPhotosAndAlbums::do(Tag $tag)`), which returns both photos and regular `Album`s carrying a given tag. Per explicit direction: **caching in this codebase happens at the SQL-query layer, not the request/response layer** — this feature has never cached a whole controller response or a whole multi-query action, only individual queries (`getChildrenPaginated()`, and each of `Top::get()`'s four constituent queries individually, per FR-053-02). Consistent with that, only `GetTagWithPhotosAndAlbums`'s **album** half (`getAccessibleAlbums()`, a private method whose query is `Album::query()->whereHas('tags', ...)` filtered by `applyBrowsabilityFilter()`) is cached here. The **photo** half (`getAccessiblePhotos()`) is untouched and remains uncached, per the existing photo-listing Non-Goal — this is not an inconsistency, it's the query-layer-caching principle applied literally: two different queries in the same action are two independent caching decisions.

`getAccessibleAlbums()` differs from `getChildrenPaginated()`/`Top()` in one important way: it filters via `AlbumQueryPolicy::applyBrowsabilityFilter()`, which (unlike `applyVisibilityFilter()`, confirmed by the original audit's §9 to depend only on `owner_id`/`access_permissions`/`users_user_groups`/`may_administrate`) additionally depends on `App\Policies\AlbumPolicy::getUnlockedAlbumIDs()` — **session-scoped** state (`Session::get(...)`), not just the requesting user. Caching this query keyed only by user id would leak: a guest (or even a different session of the same user) who hasn't entered a password could be served another session's cached, already-unlocked view of a password-protected album's presence in the tag's album list — or the reverse. FR-053-26 accounts for this explicitly.

| S-053-29 | `managed_cache_albums_enabled=false`, `managed_cache_enabled=true` — all six cached queries compute live on every call (no cache I/O attempted); toggling it back on resumes caching without a restart (config is read per-request via `ConfigManager`, not cached in a long-lived process). |
| S-053-30 | `managed_cache_albums_enabled=true`, `managed_cache_enabled=false` — still no caching for any of the six queries; the master switch wins regardless of the per-part toggle's value (AND semantics, neither switch overrides the other). |
| S-053-31 | Cache miss then hit — `GetTagWithPhotosAndAlbums::getAccessibleAlbums()`, same tag/user/unlocked-set. Second call returns cached result, zero relevant queries; the sibling `getAccessiblePhotos()` call is unaffected (always live). |
| S-053-32 | Two different sessions (same or different users) with different `getUnlockedAlbumIDs()` sets for the same tag never share a cache entry — a password-protected album's presence in the tag's album list is never leaked across an unlock boundary. Unlocking mid-session produces a cache miss (new key), not a stale locked view. |
| S-053-33 | Tagging a previously-untagged album with tag T (via `updateAlbum()`) evicts `tag:{T}`'s cached album list — the album appears on next read (negative-cache case, closed by `AlbumTagsChanged`, not by `addTags()` alone, since the cached list never referenced this album before). |
| S-053-34 | Removing tag T from an album evicts `tag:{T}`'s cached album list — the album no longer appears on next read. |
| S-053-35 | Renaming a tag (`EditTag`, implemented as merge into a new-or-existing tag) or merging two tags evicts both the source and destination tag's cached album lists; deleting a tag evicts its own cached album list. |

## Appendix

### Full mutation-surface audit

The following inventory (file:line, mechanism, existing-event-or-none) was compiled by exhaustively reviewing every code path capable of changing what `getChildrenPaginated()` or `Top()` display, before any requirement above was written. Section 10 (Tag detail page) was added afterward, during spec review, once a third consumer was identified. Kept verbatim as the evidentiary basis for the FR table; not itself normative (the FR table above is).

#### 1. `app/Actions/Album/*.php`

- `Create.php:38-51` — creates album (Eloquent `save()`), sets permissions/stats. **Dispatches `AlbumSaved` already.**
- `Delete.php:71-118` — deletes albums + descendants (raw `DB::table()` throughout: `albums`, `base_albums`, `access_permissions`, `statistics`, `tag_albums`, `person_albums`, `photo_album`, `live_metrics`, `album_user_thumbs`). **Dispatches `AlbumDeleted` per unique parent already** — but only reaches that dispatch for the regular-album branch; tag/person-album-only batches return early with zero events (closed by FR-053-10).
- `Move.php:24-46` — reparents via `appendNode()`/`saveAsRoot()` (Eloquent `save()` internally, but the vendor nested-set package also performs raw bulk `_lft`/`_rgt` shifts on sibling/ancestor/descendant rows as a side effect). **No domain event dispatched at all** (closed by FR-053-05).
- `Merge.php:29-72` — raw `photo_album` re-linking + `appendNode()` for sub-albums + delegates to `Delete::do()` for sources. **No event for the target album gaining children** (closed by FR-053-06); source-side already covered via `Delete`.
- `SetProtectionPolicy.php:32-70` — sets `is_nsfw`/public/password/grants (Eloquent `save()` ×2). **Dispatches `AlbumSaved` already** — but unconditionally, regardless of `$album`'s actual type, which is the FR-053-11 bug.
- `SetSmartProtectionPolicy.php:24-31` — smart albums, config-backed, not DB rows. **No event, and none needed** — `Top()`'s smart-album section is never cached (see `FR-053-17`, removed during review once this was noticed).
- `Transfer.php:20-34` — sets `owner_id` (Eloquent `save()`), deletes redundant `AccessPermission` (query-builder delete), `makeRoot()`+`save()`, `fixOwnershipOfChildren()` (raw bulk). **No event dispatched at all** (closed by FR-053-07/18).
- `Unlock.php` — session-scoped, no DB row mutation. Confirmed out of scope (see Non-Goals).
- `PositionData.php`, `Breadcrumb.php`, `Archive32/64/BaseArchive.php`, `ZipChunkCount.php`, `ListAlbums.php` — read-only for this feature's purposes.
- `CreateTagAlbum.php`, `CreatePersonAlbum.php` — Eloquent `save()`, **no event** (closed by FR-053-09).

#### 2. Controllers

- `AlbumController::updateAlbum()/updateTagAlbum()/updatePersonAlbum()/cover()/header()/updateAlbumHeader()/rename()/setPinned()` — all Eloquent `save()`, **none dispatch any domain event today** (closed by FR-053-04/09). `merge()`/`move()`/`transfer()` dispatch only the unrelated `AlbumRouteCacheUpdated` (Feature 040's HTTP-cache event), never `AlbumSaved`.
- `SharingController::create()/edit()/delete()/propagate()` — Eloquent + one query-builder bulk delete; `Propagate::overwrite()` is raw bulk `DB::table('access_permissions')`. **No event anywhere** (closed by FR-053-12/13).
- `Admin\BulkAlbumController` → `BulkEditAlbumsAction::do()` — Groups 1/2 are raw bulk `Model::query()->update()`; Group 3 loops `SetProtectionPolicy::do()` but only for a subset of possible payload fields. **Groups 1/2 dispatch nothing; Group 3's `is_nsfw`-only exclusion is a real gap** (closed by FR-053-08).
- `Admin\UserGroupsManagementController::addUser()/removeUser()/updateUserRole()` — raw pivot `attach()`/`detach()`/`updateExistingPivot()`. **No event** (closed by FR-053-14).
- `Admin\ModerationController` — bulk `Photo::whereIn()->update()`, dispatches `ApplyNsfwAlbumSensitivityJob` (a job, not a domain event); that job itself doesn't dispatch anything either (closed by FR-053-21).

#### 3. Photo mutations affecting album cover/listing state

- `Photo\Pipes\Shared\SetParent.php`, `Photo\MoveOrDuplicate.php`, `Photo\Rating.php` — all correctly dispatch `PhotoSaved`/`PhotoAdded`/`PhotoDeleted`/`AlbumSaved`/`PhotoMoved`/`PhotoRatingChanged` already; no gap (photo-listing itself is out of scope regardless, per Non-Goals — these are only relevant here insofar as they already correctly touch `AlbumSaved` for cover-bearing side effects).
- `DTO\Delete\PhotosToBeDeletedDTO` force-delete path — raw, **unscoped** `DB::table('albums')->whereIn('header_id'/'cover_id', $chunk)->update([...=>null])` (and same for `tag_albums`). Only `PhotoDeleted::dispatch($from_id)` fires, scoped to the *originating* album, not whichever *other* album(s) actually had their cover/header cleared. **Real, silent gap** (closed by FR-053-19). Single most surprising finding in the whole audit.
- `RecomputeAlbumStatsJob`/`RecomputeAlbumSizeJob` — write `num_children`/`num_photos`/`min_taken_at`/`max_taken_at`/`auto_cover_id_*`/size stats (exactly what the listing displays) asynchronously, **after** the event that triggered them, and dispatch nothing on completion (closed by FR-053-15).

#### 4. Console commands / import / sync

- `Console\Commands\Sync.php` and the `Actions\Import\Pipes\*` pipeline (`CreateNonExistingAlbums`, `DeleteMissingAlbums`) delegate to `Album\Create`/`Album\Delete` — **already covered**, no gap.
- `Console\Commands\FixTree.php` → vendor `nestedset` package's `fixTree()` — raw bulk SQL correcting `_lft`/`_rgt`/`parent_id` for an unpredictable set of rows. **No event** (closed by FR-053-20, coarse).

#### 5. Models — no boot observers exist

`Album`, `BaseAlbumImpl`, `AccessPermission`, `UserGroup` have **zero** Eloquent boot-time observers (`static::saved()`, `::observe()`); only `PhotoObserver`/`FaceObserver` exist and are unrelated. **All cache-relevant signaling in this feature is via explicit `::dispatch()` calls** — confirming the premise that Eloquent observers would be structurally insufficient even if used, since `Album::fixOwnershipOfChildren()` (`app/Models/Album.php:412-426`) and the vendor nested-set internals perform raw bulk `->update()` calls that don't fire per-model events regardless of whether an observer is registered.

#### 6. Runtime bulk-update commands (non-migration)

Already covered above (`BulkEditAlbumsAction`, `PhotosToBeDeletedDTO`, `FixTree`, `ApplyNsfwAlbumSensitivityJob`).

#### 7. Smart/tag/person albums — confirmed scope boundary

`TagAlbum`/`PersonAlbum` have no `parent_id` and cannot appear in `getChildrenPaginated()`'s `where('parent_id', ...)` query — correctly out of scope for that consumer. They **do** appear in `Top()` (newly in scope per the user's scope decision), specifically in their own independently-cached sub-queries (FR-053-02), which is why FR-053-09/10/11 exist. Smart albums (Favourites, Recent, etc.) are never persisted rows and their *listing appearance* in `Top()` is never cached either (computed fresh via `Gate::check()` every call) — this feature has no cache-invalidation concern for them at all (`FR-053-17` removed). Their thumbnails are a separate, unrelated, already-event-driven mechanism (`RecomputeAlbumUserThumbsJob`/`RecomputeAlbumUserThumbsOnPhotoChange`), out of scope regardless.

#### 8. Sort-order & other listing-shaping configuration

`AlbumSortingCriterion::createDefault()` reads `sorting_albums_col`/`sorting_albums_order` from `ConfigManager` whenever an album has no per-album override (`album_sorting_col`/`album_sorting_order` both null) — the common case. `Top()` separately reads `sorting_pinned_albums_col`/`sorting_pinned_albums_order` (pinned section), `deduplicate_pinned_albums` (root-query shape), and `ai_vision_face_enabled` (whether person albums are queried at all); `AlbumChildrenController` reads `albums_per_page` (page size). None of these 7 keys correspond to any `albums`/`base_albums` row — closed collectively by the single coarse-flush FR-053-16.

#### 9. `AlbumQueryPolicy::applyVisibilityFilter()` — every input

`users.may_administrate`, `base_albums.owner_id`, `access_permissions.{user_id,user_group_id,base_album_id,is_link_required,password,grants_*}`, `users_user_groups.{user_id,user_group_id,role}`. **Not read:** `base_albums.is_nsfw` (confirmed not a visibility gate for this listing — see Non-Goals).

#### 10. Tag detail page & Tag CRUD (added post-review, not part of the original 9-area sweep)

- `App\Actions\Tag\GetTagWithPhotosAndAlbums::getAccessibleAlbums()` (`Album::query()->whereHas('tags', ...)` filtered by `AlbumQueryPolicy::applyBrowsabilityFilter()`) — the only place in the codebase where "regular albums carrying tag T" are listed; distinct from `TagAlbum` (the smart-album type), which only aggregates photos. Uses **browsability**, not visibility — additionally reads `App\Policies\AlbumPolicy::getUnlockedAlbumIDs()`, which is `Session::get(...)`-backed, not a DB row, unlike everything enumerated in §9. No existing caching.
- `Actions\Tag\EditTag::do()` — delegates entirely to `MergeTag::do()`. No direct mutation, no event of its own (inherits `MergeTag`'s fix).
- `Actions\Tag\MergeTag::handleAlbums()` — **raw** `DB::table('albums_tags')` insert + delete, already computes the exact affected album id set (`$source_album_ids`) but discards it after use. **No event.**
- `Actions\Tag\DeleteTag::do()` — **raw** `DB::table('albums_tags')->whereIn('tag_id', $tag_ids)->delete()` (and the equivalent for `photos_tags`, out of scope). **No event.**
- No boot-time observers on `Tag`, `Album`'s `tags()` pivot, or `albums_tags` — consistent with audit finding §5 (no Eloquent observers exist anywhere in this mutation surface).

### Relationship to Feature 052

Feature 052 shipped `ManagedCacheService` itself and designed (but did not implement) invalidation wiring for one of the two consumers this feature targets (`getChildrenPaginated()`; its other original pilot, `PhotoRepository::getPhotosForAlbumPaginated()`, is explicitly out of scope here — see Non-Goals), then explicitly reworked away from that design in favor of an undesigned "per-part cache configuration" direction (its Goal 4). This feature does not wait for that redesign — it resumes and substantially expands `getChildrenPaginated()`'s caching (album-tree gaps found by the full audit go well beyond Feature 052's original 3), and adds two consumers Feature 052 never designed at all (`Top()`'s four queries, the Tag detail page's album query), all gated by the master `managed_cache_enabled` switch plus a dedicated `managed_cache_albums_enabled` toggle (Goal 6/FR-053-25, added via the new `rememberIf()` method). In the process it finally ships the config migration (T-052-05) and Settings visibility patch (T-052-06) Feature 052 left undone. `managed_cache_albums_enabled` is a hardcoded, single-purpose toggle, not an implementation of Feature 052's Goal 4 — if that generic per-part configuration system is picked up later, it would most likely wrap around (or replace) this feature's toggle with a dynamic one, not the other way round.
