This feature applies the existing Struct-of-Arrays convention (ADR-0009) and the existing `bucket_id`-driven virtual-scroll pattern (Feature 061/062/063) to photos — it does not establish a new convention, so no new ADR is added.

## Overview

Feature 064 built the photo-listing Struct-of-Arrays (SoA) backend — three tiers (`buckets`, `ratios` at the bare `GET /Albums/{album_id}/Photos` path, and bounded on-demand `details`) scoped to one album's direct photos, gated by `modules.is_struct_of_array_enabled`. It explicitly deferred frontend adoption (NG1: "a separate follow-up feature, mirroring Feature 063, is required"). This feature is that follow-up, mirroring Feature 063's relationship to Feature 061/062 exactly: it wires a virtualized photo grid to Feature 064's three tiers, leaves the v2 paginated path (`AlbumPhotosController`, `PhotoRepository::getPhotosForAlbumPaginated()`) completely untouched and coexisting, and gates everything behind the existing flag with no new backend surface.

The core technical difference from Feature 063's own adoption work is aspect ratio uniformity. Every album tile Feature 063 virtualized shares one fixed CSS aspect ratio, so a uniform-tile row-count algorithm (`buildVirtualAlbumRows()`) was sufficient. Photos carry a genuine per-photo `ratios[i]` value from tier 2, and today's v2 `justified`/`square`/`masonry`/`grid` layout modes already solve their respective packing problem via a DOM-measurement-driven WASM call each (`useJustify.ts`/`useSquare.ts`/`useMasonry.ts`/`useGrid.ts` all read live child nodes, call the matching `@lychee-org/layouts` primitive, then write absolute-position styles back onto those same nodes). That DOM-round-trip is what's incompatible with virtualization, not the packing algorithm itself: every one of those four WASM primitives already accepts a plain `Float64Array` of ratios (or count, for size-uniform modes) and returns exact `{x, y, width, height}` box geometry with **no DOM dependency in its own signature** — the DOM-reading/DOM-writing is entirely the surrounding `useX.ts` wrapper's own choice, not a constraint of the underlying computation. Because a tile's box is therefore knowable the instant tier 2 resolves, regardless of which of the four algorithms computed it, this feature virtualizes **all five** layout modes (`justified`/`square`/`masonry`/`grid`/`list`) through one shared mechanism: compute every tile's exact box up front per bucket (calling the matching WASM primitive directly, DOM-free — `list` needs no WASM call, just fixed-height row arithmetic), then virtualize generically by grouping the resulting, already-known box list into fixed-size "chunks" of exact (never estimated) height and mounting only the chunks currently within the viewport's overscan range. A chunk is a pure virtualization bookkeeping unit, not a layout concept — this is what lets `useWindowVirtualizer` (row-indexed by design) drive a virtualized view of geometry that isn't actually organized into uniform rows at all.

A second structural difference from Feature 063: v2's photo listing has two axes of client-configurable behaviour Feature 063's album tiles never had — five distinct layout modes (`justified`/`square`/`masonry`/`grid`/`list`) and server-side tag/person filtering (`AlbumService.getPhotos(albumId, page, tag_ids, tag_logic, person_id)`). Feature 064's tiers support neither: they return exactly one whole-album, unfiltered, layout-agnostic dataset (`ratios`/`buckets`/`details`), with tag/person filtering explicitly out of scope (NG8). This feature makes an explicit, scoped decision about both axes — full virtualization coverage for every layout mode (Goals G3/G4, Decision Card Q-065-01) but a v2 fallback for the filtering axis (Non-Goal NG4) — rather than attempting full parity in one pass, following this repository's established precedent of narrowing an adoption feature's first increment rather than blocking on total parity (Feature 063 itself shipped without photo virtualization at all, then expanded scope twice by addendum).

A third, favourable difference: unlike albums, where Feature 063 discovered mid-implementation (Q-063-01) that fetch/boundary state and the rendered tile array live in two different stores, photos already have a clean singular/plural store split — `resources/js/stores/PhotoState.ts` (the currently-open lightbox photo only) and `resources/js/stores/PhotosState.ts` (the listing array, timeline split, rating filter). The orchestrating fetch actions for both albums' and photos' listings already live together in `resources/js/stores/AlbumState.ts` (`loadAlbums()`/`loadAlbumsV3()` alongside `loadPhotos()`/`appendPhotos()`/`prependPhotos()`), so this feature's new `loadPhotosV3()` dispatcher is added there, directly alongside Feature 063's own `loadAlbumsV3()`, writing adapted tiles into `PhotosState.ts.photos` — the same "write into the field the v2 path already populates, no new tile-array field" discipline Feature 063 established for `AlbumsState.ts.albums` (FR-063-06).

Affected modules: UI only (Vue 3 + Pinia, v8). No backend/core/CLI change — Feature 064's three routes, resources, and jobs are consumed as-is, byte-identical.

## Goals

- **G1:** Expose one centralized, computed `isPhotoSoaActive` getter on `AlbumState.ts` — `is_struct_of_array_enabled` AND the current parent is a regular `Album` AND no tag/person filter is active — read by **every** SoA-photo-path consumer (the fetch dispatcher below, FR-065-09's render dispatcher, FR-065-13/14's on-demand `details` fetch, FR-065-16's drag-select) instead of each re-deriving the same condition independently (resolved via Q-065-05, Option A). Add a flag-aware dispatcher (`loadPhotosAuto()`, mirrors `loadAlbumsAuto()`) to `AlbumState.ts` that reads `isPhotoSoaActive` and, when true, fetches tier 1 (`buckets`) + tier 2 (`ratios`) in parallel via a new `photo-children-v3-service.ts`; when false, falls back to the existing v2 paginated `loadPhotos()` unchanged.
- **G2:** Derive per-bucket boundaries from tier 1's `{bucket_ids, counts, labels, bucketable}` against tier 2's already-ordered `ratios` rows via a pure positional walk — reusing `computeBucketBoundaries()` from `resources/js/v8/utils/albumBucketBoundaries.ts` as-is (already generic over any `{bucket_ids, counts}`-shaped tier 1 payload plus a flat row count; no photo-specific fork needed), not a new client-side join/sort.
- **G3:** Ship one unified, analytic virtualization mechanism covering **all five** layout modes — `justified`/`square`/`masonry`/`grid` (each computed by calling its matching WASM primitive directly against `ratios[]`/tile count, zero DOM dependency) and `list` (trivial fixed-height row arithmetic, no WASM call) — by computing every tile's exact box up front per bucket, then grouping the resulting box list into fixed-size, exact-height "chunks" fed to `useWindowVirtualizer` as its row unit, mounting only chunks within the viewport's overscan range. Sticky bucket headers, sourced from tier 1's `labels[]`, apply uniformly to all five modes, bypassing `splitter.ts` entirely — exactly as FR-063-08 did for albums, now without the row-based/column-based distinction an initial narrower framing of this feature assumed (Decision Card Q-065-01).
- **G4:** Within a mounted chunk, absolutely position every contained tile from its precomputed box (offset relative to the chunk's own top) via one shared tile-rendering component per visual shape (`PhotoThumbVirtual.vue` for the four grid-shaped modes, `PhotoListItemVirtual.vue` for `list`) — by the time any tile is rendered, its exact box is already known regardless of which of the five modes' geometry produced it, so the rendering step itself needs no per-mode branching beyond "which visual shape."
- **G5:** Add an on-demand, bounded `details` fetch (`loadPhotoDetails(ids)` on `PhotosState.ts`, backed by a `detailsById` cache map) triggered only when a UI surface actually needs tier-3 fields — opening the lightbox, opening an edit dialog that needs description/EXIF/license/tags — never an eager whole-album or whole-bucket prefetch, respecting FR-064-09's own caller-side discipline (a client should consult `counts[]` before choosing `bucket_id` mode; this feature never uses `bucket_id` mode at all in v1, only bounded `photo_ids[]` chunks of at most a handful of ids at a time).
- **G6:** Rewire `PhotoState.ts`'s lightbox getters (`imageViewMode`, `style`/`previousStyle`/`nextStyle`, `srcSetMedium`) to read from whichever data is available — the lightweight `ratios`-derived tile immediately, the richer `details`-derived data once G5's fetch resolves — without changing their external computation logic, and derive next/previous navigation purely from the already-loaded, already-ordered `ids` array (never from a backend `next_photo_id`/`previous_photo_id` field, matching Feature 064's own NG5 resolution that v2's `PhotoResource` never populates those fields in this exact album-listing context either).
- **G7:** Reimplement `dragAndSelect.ts`'s photo-selection geometry (`getPhotoBoxesV3()`, mirrors `getAlbumBoxesV3()`) as a single, mode-agnostic function covering all five layout modes — intersecting the drag rectangle against the already-computed box list (G3) regardless of a tile's current mount state. No DOM-query fallback (`getBoxes("data-photo-id")`) is needed for any mode on the SoA path, since box geometry is always known the moment tier 2 resolves.
- **G8:** Wire the existing mutation-triggered refresh cascade (upload completion, delete, move/copy, rename, star/highlight toggle, rating change, tag edit, license edit, apply-renamer) to re-invoke `loadPhotosAuto()` and evict any affected id from `detailsById`, mirroring FR-063-13's "no dedicated re-fetch action needed — extend the existing cascade" discipline.
- **G9:** Reuse the existing `phpDateFormat.ts` (built by Feature 063) against the existing, currently-frontend-unused `date_format_photo_thumb` config to render a v3 tile's date client-side, and against the existing `timeline_photo_date_format_hour`-driven label for the photos-only `HOUR` bucket granularity (FR-064-06) — no new config fields, unlike Feature 063's two new album-only fields.
- **G10:** Preserve `aria-posinset`/`aria-setsize` correctness on virtualized tiles, mirroring NFR-063-07.

## Non-Goals

- **NG1:** No further album/sub-album changes — Feature 063 already owns that surface entirely; this feature touches only the photo-listing section already delegated to `PhotoThumbPanel.vue` today.
- **NG2:** No v2 backend or v7 change of any kind. `AlbumPhotosController`, `GetAlbumPhotosRequest`, `PhotoRepository::getPhotosForAlbumPaginated()`, `PaginatedPhotosResource`, and every `resources/js/v7/**` file stay byte-identical (NFR-065-01/08).
- **NG3:** No modification to `useJustify.ts`/`useSquare.ts`/`useMasonry.ts`/`useGrid.ts` or to the `@lychee-org/layouts` WASM package itself (touching the WASM package's own build is separately costly — its UMD embed bundle requires manual byte-inlining, not the default loader). This feature adds new, separate, DOM-free TypeScript callers (FR-065-07) alongside the existing DOM-based ones; the existing four `useX.ts` wrappers remain exactly as-is, continuing to serve the v2 fallback paths (NG4/NG5) unchanged.
- **NG4:** No tag-filtered or person-filtered SoA path. Feature 064's tiers accept no `tag_ids`/`tag_logic`/`person_id` parameters at all (its own NG8). When a tag filter or person filter is active in the UI, `loadPhotosAuto()` always falls back to the v2 paginated `loadPhotos()` regardless of the flag or layout mode (Decision Card Q-065-02). Requesting a Feature 064 amendment to add filter parameters is left to a future feature if this gap proves disruptive in practice.
- **NG5:** No `TagAlbum`/`PersonAlbum`/`BaseSmartAlbum`-hosted ("matching photos") listings on the v3 path — mirrors Feature 064's own NG3 exactly (those routes 404 for non-`Album` parents server-side). `loadPhotosAuto()` always uses v2 when the current browse context is not a regular `Album`.
- **NG6:** No new feature flag. Reuses `modules.is_struct_of_array_enabled` as-is, consistent with Feature 058/061/063's own precedent.
- **NG7:** No automated frontend test suite. The repo has none (confirmed Feature 049, reaffirmed Feature 058/063); verification is manual/browser-based.
- **NG8:** No new photo-level `/rights` endpoint or client-side rights-combination formula. Feature 064 deliberately exposes no such endpoint (its own NG9) — every action a photo's context menu needs beyond the single owner-gated rating rule (Feature 059) is already sourced from the containing album's own uniform rights object exactly as v2 does today; only `owner_id` (present unconditionally in both `ratios` and `details`) is ever compared client-side, and only for that one rule. Unlike Feature 063's FR-063-04/FR-063-05, there is no broader rights-combination logic to build or a rights-owner-shortcut bug class to guard against here.
- **NG9:** No change to `PhotoState.ts`'s slide-transition math (`transition`, `style`/`previousStyle`/`nextStyle` CSS-string construction) beyond swapping which underlying object its getters read (G6) — the computation itself is unchanged.
- **NG10:** No windowed/paginated re-implementation of tier 2 on the frontend. `ratios` is whole-album-at-once by design (Feature 064 G3); this feature never introduces a page/offset concept for it. The existing `photos_current_page`/`_last_page`/`_per_page`/`_total`/`photos_min_page` bookkeeping in `AlbumState.ts` stays exactly as-is, exercised only by the v2 fallback paths (NG4/NG5).
- **NG11:** No visual redesign of tile appearance beyond what the data shape forces. Unlike Feature 063's album tiles (which lost the video-play icon and blur-up placeholder because tier 2 for albums omits those fields), photo tier 2 (`ratios`) already carries `is_videos`/`is_raws`/`is_live_photos`/`is_highlighteds`/conditionally `rating_avgs`/`thumb_infos`/`tags` unconditionally per-row — so the video/raw/live-photo/highlighted/rating badges and title-or-description overlay all render identically to v2 for all five virtualized modes with **zero** accepted regression there. Three accepted regressions in total. **(1)** Mirroring Feature 063's own: no blur-up placeholder fade-in on first paint, since neither `ratios` nor the cover-resolution mechanism (`<Thumb>`, Feature 056 Asset endpoint) carries a placeholder/blurhash value outside the bounded `details` tier's nested `size_variants.placeholder`. **(2)/(3)** Resolved via Q-065-06, Option A: hover-triggered face-recognition prefetch (v2's `prefetchFaces()`, gated by `photo.face_count > 0`) becomes a no-op on the virtualized path, since `face_count` exists only in the bounded `details` tier, not `ratios`, and fetching `details` eagerly for every rendered tile would defeat G5's on-demand-only discipline; and `PhotoListItemVirtual.vue`'s metadata row omits the file-size chip `PhotoListItem.vue` shows today (`photo.preformatted.filesize`), for the identical reason — no lightweight file-size field exists in `ratios`, and `details` is deliberately never fetched eagerly per tile. No Feature 064 amendment was requested for either gap.
- **NG12:** No bulk/eager prefetching of `details` for an entire visible bucket or the whole album. G5 is strictly on-demand, id-at-a-time (or a small handful for lightbox neighbor preview). A bulk-prefetch optimization is left to Follow-ups/Backlog.
- **NG13:** No change to `contextMenu.ts`'s own logic or external contract — it already operates on already-resolved selection state (ids/rights), not on how that state was fetched, so it needs no modification; only individual `PhotoCallbacks` that require detail-tier fields gain a details-fetch-before-open step (G5), which lives in the calling dialog component, not in `contextMenu.ts` itself.

## Appendix

### Decision Cards

#### Q-065-01 — Which layout modes get SoA virtualization in v1?

**Options considered:**
- **A.** All five layout modes (`justified`/`square`/`masonry`/`grid`/`list`) get a virtualized, analytic rendering path in this feature.
- **B.** Only the three uniform-row-height modes (`justified`/`square`/`list`) get virtualization; `masonry`/`grid` (column-balanced) keep their existing DOM-mounted rendering, just re-sourced from SoA data, deferring their virtualization to a future feature.
- **C.** Only `justified` (the most commonly used mode, and the one `virtual-scrolling-study.md` most directly motivates) gets virtualization in v1; every other mode stays entirely on the v2 path.

**Resolved: Option A.** Option B rests on treating `masonry`/`grid` as a structurally harder problem than row-packing — but that framing conflates "the packing algorithm is more complex" with "the tile geometry is harder to virtualize," and only the first is true. All four non-`list` v2 layout modes are already WASM-driven (`justified()`/`square()`/`masonry()`/`grid()`, `resources/js/v8/layouts/wasmLayouts.ts`), and every one of those primitives already returns exact `{x, y, width, height}` box geometry from a plain `Float64Array` with **no DOM dependency in its own signature** — the DOM-reading/DOM-writing is entirely each mode's thin `useX.ts` wrapper's own choice, not a constraint of the underlying computation (see Q-065-04). Since a tile's box is therefore knowable the instant tier 2 resolves regardless of which of the four algorithms computed it, virtualization becomes a question the analytically-known box list can already answer uniformly for any of the five modes — "does this box's `y`/`height` overlap the current viewport" — with no dependency on whether the layout that produced it happens to be organized into literal rows. Option A costs no more new algorithmic work than Option B: `computeAnalyticPhotoLayout()` (FR-065-07) is one function with a per-mode branch to the matching WASM call (or trivial arithmetic for `list`), and the chunked virtualization mechanism built on top of it (FR-065-08/09, Q-065-04) is entirely mode-agnostic. Option A also avoids Option B's own accepted cost — a permanent inconsistency where `masonry`/`grid` never surface tier 1's non-date bucket dimensions and never benefit from bounded DOM mount count — for no remaining benefit once the "different algorithm class" premise is corrected.

#### Q-065-02 — How should tag/person-filtered photo views behave when the SoA flag is on?

**Options considered:**
- **A.** Request a Feature 064 amendment adding `tag_ids`/`tag_logic`/`person_id` parameters to all three tiers before starting this feature's frontend work.
- **B.** Fall back to the existing v2 paginated `loadPhotos()` whenever a tag or person filter is active, regardless of the flag, and revisit the amendment only if this proves disruptive in practice.

**Resolved: Option B.** Feature 064 already logged this exact gap as its own NG8, explicitly framed as "left for a future amendment if requested" — treating it as blocking this feature's entire start would delay virtualization for the overwhelming majority of album views (unfiltered) to solve a problem only the filtered-view minority has. The fallback is structural and narrow (one additional condition in `loadPhotosAuto()`'s existing dispatch, FR-065-02/NG4), not a new code path to maintain, and it degrades to exactly today's behaviour for that view rather than to a broken or inconsistent one.

#### Q-065-03 — Eager whole-album `details` prefetch vs. on-demand, bounded fetch?

**Options considered:**
- **A.** Prefetch `details` for the entire album (or entire visible bucket) immediately after tier 1+2 resolve, mirroring how Feature 063 eagerly background-fetched its own tier 3 (rights) for every album child.
- **B.** Fetch `details` strictly on demand — one to a few ids at a time, only when a UI surface (lightbox, edit dialog) actually needs tier-3 fields.

**Resolved: Option B.** Feature 063's tier 3 (rights) is a small, uniform-shaped payload safe to fetch for an entire album's children at once. Feature 064's `details` tier is explicitly the heavy tier — nested `size_variants` (9 variants), `palette`, `statistics`, EXIF, GPS — and its own spec explicitly frames the client as responsible for choosing a bounded scope rather than the backend protecting against an oversized request (`bucket_id` mode is deliberately *uncapped*, precisely because the backend trusts the client to consult `counts[]` first). Eagerly prefetching an entire five-figure album's `details` would be exactly the unbounded-payload problem Feature 064's own three-tier split was designed to avoid. On-demand fetching, bounded to the one to three ids a lightbox or dialog genuinely needs at any moment, is the only option consistent with that design intent.

#### Q-065-04 — How can a row-indexed virtualizer (`useWindowVirtualizer`) virtualize layouts (`masonry`/`grid`) that aren't organized into literal rows at all?

**Options considered:**
- **A.** Port each mode's `useX.ts` DOM-measurement approach as-is, forcing every tile (even off-screen ones) to mount briefly so its geometry can be read — and, for `masonry`/`grid`, treat "no literal row concept" as disqualifying them from virtualization entirely (this feature's initial, narrower framing, corrected by Q-065-01).
- **B.** Compute every tile's exact box analytically from the already-known `ratios: float[]`/count, calling the matching WASM primitive directly (each already accepts a plain input array with no DOM dependency in its own signature) inside one shared pure function; then virtualize by grouping the resulting, already-known box list into fixed-size "chunks" — a pure bookkeeping unit with an exact, precomputed height, unrelated to any visual row — and feed those chunks to `useWindowVirtualizer` as its row unit, absolutely positioning every tile within a mounted chunk from its own precomputed box.

**Resolved: Option B.** Option A defeats the entire purpose of virtualization for the two modes it would apply to — it would require every off-screen photo to exist in the DOM at least transiently, reintroducing the exact cost this feature exists to remove — and its "disqualify column-balanced layouts" corollary rests on an unnecessary conflation of "this algorithm doesn't produce literal rows" with "this algorithm's output can't be virtualized" (Q-065-01). Every ratio/count needed to compute exact geometry is already known the moment tier 2 resolves, before any tile ever mounts, for all five modes equally — this makes the analytic approach not just feasible but strictly simpler: `computeAnalyticPhotoLayout()` (FR-065-07) calls the matching WASM primitive once per bucket, and the chunking step (FR-065-08) that follows never needs to know or care whether the boxes it's grouping came from a row-based or column-based packing algorithm, since it groups by tile-count/height-budget, not by any layout-native "row." `PhotoGridVirtual.vue`/`getPhotoBoxesV3()` (FR-065-09/16) then consume that one shared `ChunkedAnalyticPhotoBoxList` shape (DO-065-03) identically for all five modes, reusing Feature 063's own outer-scaffolding decisions (`useWindowVirtualizer`, two-layer sticky headers, `Virtualized/` directory placement) unchanged.

#### Q-065-05 — Should "is the SoA photo path active" be one centralized flag, or independently re-derived per consumer?

**Options considered:**
- **A.** One centralized computed `isPhotoSoaActive` getter on `AlbumState.ts`, read by the fetch dispatcher, render dispatcher, on-demand `details` fetch, and drag-select alike; `loadPhotoDetails()` explicitly no-ops when it's `false`.
- **B.** Each consumer independently re-derives the same three-part condition; `loadPhotoDetails()` fires unconditionally and relies on FR-064-09's "curate, don't error" convention to degrade gracefully.
- **C.** Infer "already has full data" by duck-typing the tile's own shape (does it already carry `description`/`size_variants`?) rather than an explicit flag.

**Resolved: Option A** (confirmed by user, 2026-09-06). FR-065-13/14's on-demand `details` fetch, as originally drafted, fired unconditionally on lightbox/dialog-open with no check against the same three-part condition FR-065-02's fetch dispatcher already computes — a real correctness gap, since Feature 064's endpoints 404 for non-`Album` parents (NG5) and a tag/person-filtered view (NG4) already has complete v2 data, making the fetch either erroring or purely wasted in both fallback cases. Option B's reliance on graceful degradation only papers over the wasted-request case and does nothing for the 404 case. Option C is more fragile than a boolean — this spec elsewhere (FR-065-04) deliberately distinguishes "field omitted by a server gate" from "field absent because a different code path never populates this shape at all," and duck-typing conflates the two. Option A costs one small piece of shared state in exchange for a single source of truth that FR-065-02/09/13/14/16 all reference, eliminating drift risk between them by construction.
