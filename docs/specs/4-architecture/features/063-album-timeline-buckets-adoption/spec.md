## Overview

Feature 061 shipped three backend-only v3 endpoints for an album's direct children — `GET .../children/buckets` (bucket counts + ready-to-render labels), `GET .../children` (per-child render data, whole-album-at-once), `GET .../children/rights` (background-fetched permission signals) — deliberately without a frontend consumer. This feature is that consumer: it replaces the subalbum section of `AlbumPanel.vue` (today driven by `AlbumState.ts`'s v2 `loadAlbums()`/`loadMoreAlbums()`, paginated through `AlbumChildrenController`) with a virtual-scrolled rendering fed by all three endpoints, **entirely behind the existing `is_struct_of_array_enabled` flag** (Feature 058's flag) — mirroring Feature 058's relationship to Feature 057 exactly, and explicitly called out as the intended next step in Feature 061's plan.md Follow-ups.

`AlbumChildrenDataController` (tier 2) orders its rows by `bucket_id` first (mirroring tier 1's own bucket ordering exactly, `"unknown"` always last), then by the effective per-child sort criterion (FR-061-26) — so tier 2's flat response arrives already grouped and ordered to match tier 1's bucket boundaries. This feature's store therefore only needs a **positional walk** using tier 1's per-bucket `counts` to find section boundaries, never a client-side join, group-by, or sort.

Four things still make this more than a data-source swap (unlike 058's three consumers, which kept v2's rendering model and only changed the fetch):

1. **No pagination at all.** Tier 2 returns every direct child in one response — up to the confirmed real-world scale of 7,000+ children under one parent. Rendering that many tile components simultaneously (today's plain `v-for`, per `virtual-scrolling-study.md`'s "Current architecture" findings) would be the exact DOM-node/mount-cost blowup that study document warns about. This feature introduces real windowed rendering for the album grid — the first virtual-scroll consumer in this codebase for a multi-column tile grid (a single-column precedent already exists: `AlbumNavTree.vue`'s `useVirtualizer` usage, which this feature's grid virtualizer extends from one column to N).
2. **Sticky headers must come from the server's bucket aggregation, not client-side re-derivation.** Today's `AlbumThumbPanel.vue`/`splitter.ts` groups an already-loaded flat array by each item's own `.timeline.time_date` field, re-scanning the whole array on every reactive change. This feature instead trusts tier 1's `{bucket_ids, counts, labels}` as the authoritative section boundaries and header text — zero client-side date math (FR-061-18 already promises ready-to-render labels for exactly this reason).
3. **Right-click/multi-select rights are combined client-side, not server-computed.** Feature 061 deliberately ships raw `owner_id`/`can_delete_children`/`can_move_children`/`grants_edit`/`grants_download` signals rather than the combined `can_edit`/`can_download`/`can_delete`/`can_move` booleans `contextMenu.ts` actually reads per selected album today. This feature implements that combination, matching `AlbumPolicy::canEdit`/`canDownload`/`canDelete`'s real logic exactly (verified against `app/Policies/AlbumPolicy.php`, see FR-063-04).
4. **Cover pixels are resolved per-tile via Feature 056's existing asset endpoint, not an embedded URL.** Tier 2 supplies only `cover_id` (a photo id, nullable) — deliberately no thumbnail URL, media `type`, or blur `placeholder` (Feature 061 Non-Goals: "resolving `cover_id` to actual pixels ... is the caller's job via the existing Feature 056 Asset endpoint"). Today's `AlbumThumb.vue`/`AlbumThumbImage.vue` instead expects a pre-built URL string embedded in the v2 listing JSON (`ThumbResource.thumb`/`thumb2x`/`placeholder`, server-rendered from `Thumb::thumbUrl()` etc.) — a shape tier 2 never produces, so that pair cannot be reused unchanged for the flag-on tile image. This feature instead forks a new tile component that resolves each cover the same way `AlbumNavTree.vue` already does for its own (single-column, already-virtualized) tree nodes: `<Thumb :album-id :photo-id :type>` (`resources/js/v8/components/thumbs/Thumb.vue`), which calls `ThumbAssetService.acquire()` against `GET /api/v3/Asset/{album_id}/{photo_id}/{size_variant}` and converts the returned blob into an object URL — fired lazily per mounted tile, release()-d on unmount, which composes naturally with virtualization (only visible tiles ever acquire an asset; scrolling one out releases it, exactly as `virtualAlbumRows.ts`'s mount/unmount cycle already drives).

The three endpoints are fetched together on album navigation (not paginated further), with tier 3 (rights) fetched in the background immediately after tier 1+2 render — exactly the sequencing Feature 061's Overview specifies. `TagAlbum`/`PersonAlbum` browsing is included (Feature 061 built tier 2/3 support for both via FR-061-24/25 specifically so this feature could consume it uniformly, matching today's v2 behavior where `AlbumPanel.vue`'s subalbum section already renders identically regardless of the browsed album's type).

**2026-09-02 addendum — full root-gallery SoA adoption (FR-063-20..31, Q-063-14/15/16):** Feature 062 shipped five root/category listing endpoints (`GET /Albums/smart`, `/tags[/rights]`, `/persons?scope=`, `/pinned?scope=`, `/root[/buckets|/rights]?scope=`) with zero frontend consumer, flagged in `roadmap.md`'s Feature 062 entry as "a follow-up feature." This addendum was originally scoped to `/Albums/smart` alone (FR-063-20..23 below, Q-063-14), but the user clarified the actual intent afterward: *"the point of the extension is to support Struct-of-Array on the root gallery page"* (Q-063-16) — i.e. all five endpoints, not just smart albums. The scope below reflects that full adoption.

The five endpoints split into two structurally different groups, consumed two different ways:
- **Flat category listings** (`/smart`, `/tags`, `/persons`, `/pinned`) — curated/bounded by config or an admin's taxonomy, never by photo volume (Feature 062 NG3/NG9), so no bucketing/virtualization is warranted: these are data-source swaps in the Feature 058 sense (FR-063-20/21/25/26/27), writing adapted tiles into the existing `AlbumsState.ts` fields (`baseSmartAlbums`/`tagAlbums`/`personAlbums`/`pinnedAlbums`) those fields already hold in v2, so `Albums.vue`'s smart-albums and pinned-albums sections need zero template changes for these four.
- **`/Albums/root[/buckets|/rights]`** — root albums get the *same* tier1/2/3 bucket shape sub-album children already have (`AlbumRootController` literally reuses `AlbumBucketResource`/`AlbumChildrenDataResource`/`AlbumChildrenRightsResource`), for both `own` and `shared` scope (`shared`'s `bucket_id` carries each row's owner id — a *live* `GROUP BY owner_id`, Feature 062 FR-062-04/05, never the persisted date/title column). This *does* need the same virtualized-grid-with-sticky-headers treatment sub-album children got in Feature 063's original scope — reused via new root-scope forks of the existing Virtualized/ components (FR-063-24), not a prop-driven generalization of the originals (this repo's established "fork rather than branch a mode into a shared component" convention, applied here too — see Q-063-17).

One real gap surfaced while scoping the smart-albums slice specifically: `GET /Albums/smart` deliberately never resolves a cover photo (`cover_ids` always `null`, "zero-SQL-query" by design), whereas today's v2 listing shows a real per-viewer cached cover for every smart-album tile (`ThumbAlbumResource`/`CachesAlbumUserThumb`). Per user decision (Q-063-15), this is fixed at the source rather than accepted as a regression: Feature 062's `AlbumCategoryController::smart()` gains a batched, cache-only `AlbumUserThumb` lookup (FR-062-16, no live photo query — the same cache `RecomputeAlbumUserThumbsJob`/`BaseSmartAlbum::getThumbAttribute()` already read/write today for the v2 path), and Feature 056's `GetPhotoAssetRequest::isPhotoOfAlbum()` gains the same cache-backed cover exception `TagAlbum`/`PersonAlbum` already have, extended to `BaseSmartAlbum` (FR-056-08), so a cached cover that has since fallen out of the smart album's live query condition (e.g. unstarred before `RecomputeAlbumUserThumbsJob` catches up) still resolves through the Asset endpoint instead of 403ing. Getting FR-056-08's branch to actually fire also required fixing a separate, pre-existing bug (discovered only because a genuinely non-`Album`/`TagAlbum`/`PersonAlbum`-shaped id was finally exercised against it): `GetPhotoAssetRequest::rules()` validated `album_id` via `RandomIDRule` (fixed length/charset, matching real `Album`/`TagAlbum`/`PersonAlbum` ids only) instead of `AlbumIDRule` (the rule `GetAlbumRequest`/`GetAlbumHeadRequest` already use, which also accepts a `SmartAlbumType` value) — every smart-album Asset request 422'd before ever reaching `isPhotoOfAlbum()`; swapped to `AlbumIDRule`.

A second, unrelated pre-existing bug surfaced while building the own/shared root grid's aspect-ratio math: `RootConfig.php`'s `album_thumb_css_aspect_ratio` property carried a stray `#[LiteralTypeScriptType('App.Enum.AspectRatioType')]` override forcing the wrong generated TypeScript type (`AspectRatioType`, raw ratio strings like `"5/4"`) despite the PHP property itself being correctly typed `AspectRatioCSSType` (CSS class strings like `"aspect-5x4"`) and correctly computed via `->css()` — `AlbumConfig.php`'s sibling property has no such override and was always correct. Nothing previously read `rootConfig`'s copy of this field through `aspectRatioCssToNumber()` (the sub-album grid only ever reads `albumStore.config`'s copy), so the mistyping was latent until this addendum's root grid needed it. Removed the override.

## Goals

- New Pinia store logic — extending `resources/js/stores/AlbumState.ts` (singular; the per-navigation store, not the `.albums`-array `AlbumsState.ts`) with the tier 1/2/3 fetch/state (`bucketsV3`, `boundariesV3`, `bucketableV3`, `loadAlbumsV3()`/`loadAlbumsV3Rights()`), while the adapted tiles themselves are still written into `resources/js/stores/AlbumsState.ts`'s existing `albums` field (plural; the store `AlbumPanel.vue`'s subalbum section already reads from) — that, when the flag is on, fetches tier 1 (`GET .../children/buckets`) and tier 2 (`GET .../children`) together on album navigation, and derives bucket-section boundaries from tier 2's already-ordered flat array via a positional walk keyed by tier 1's per-bucket `counts` (Feature 061 FR-061-26 guarantees tier 2's row order matches tier 1's bucket boundaries exactly — no client-side grouping or sorting needed).
- Background-fetch tier 3 (`GET .../children/rights`) immediately after tier 1+2 resolve — not on right-click/selection — and reactively merge it into each child's rights once it arrives; every right defaults to `false` until the background fetch resolves (safe default, matches Feature 061's Overview sequencing intent).
- Implement the client-side rights-combination logic Feature 061 deliberately left unimplemented: `can_edit = (isRegularAlbumParent && owner_id === current_user.id && may_upload) || grants_edit[i]`; `can_download = (isRegularAlbumParent && owner_id === current_user.id) || grants_download[i]`; `can_delete = (isRegularAlbumParent && owner_id === current_user.id) || can_delete_children`; `can_move = (isRegularAlbumParent && owner_id === current_user.id) || can_move_children` — verified to match `AlbumPolicy::canEdit`/`canDownload`/`canDelete`'s actual logic (`app/Policies/AlbumPolicy.php:255-269,184-207,281-303`). The owner-based shortcut only holds when the browsed parent is a real `Album` (`isRegularAlbumParent`, sourced from `albumStore.modelAlbum !== undefined`): `owner_id` is "the parent `album_id`'s own `owner_id`" (FR-061-20), which equals every direct child's owner for a regular `Album` parent, but for a `TagAlbum`/`PersonAlbum` parent is the tag/person's own unrelated owner — applying the shortcut there would over-grant rights to a caller who merely owns the browsed tag/person grouping. `may_upload` is not exposed by `UserResource`; `RootAlbumRightsResource.can_upload` already carries the equivalent value (`AlbumPolicy::canUpload($user, null)` resolves to exactly `$user?->may_upload ?? false`) and is reused via `albumsStore.rootRights?.can_upload` instead of adding a new field.
- Adapt each child into an `AdaptedAlbumTile` object (`ThumbAlbumResource` plus `cover_id`, DO-063-01) — client-side-constructed `rights`, `timeline` left `null` — no longer needed once buckets drive sectioning, `thumb` left `null` — no pre-built URL exists, see the new tile-image component below, `is_pinned`/`is_public`/`is_link_required` mapped straight through from tier 2 (FR-061-27), `formatted_min_max` computed client-side (FR-063-16) — so `contextMenu.ts` and every other metadata/rights consumer of `ThumbAlbumResource` need zero changes to their own field contracts.
- New `AlbumThumbVirtual.vue` (under the same new `Virtualized/` directory as the grid/list renderers) — the tile component actually mounted per child in the flag-on grid/list, forked from `AlbumThumb.vue` rather than reusing it unchanged (this repo's established v8 convention: fork a shared component rather than branching its internals on a flag). It reuses `AlbumThumb.vue`'s existing sub-components as-is for everything that doesn't depend on a pre-built thumb URL — `AlbumThumbOverlay.vue`, `AlbumThumbDecorations.vue`, `ThumbBadge.vue`, the responsive width/`aspect-*` classes, selection/drag styling, `data-album-id` — but replaces `AlbumThumbImage.vue`'s pre-built-URL image resolution with `<Thumb :album-id="child.id" :photo-id="child.cover_id" type="thumb">`, mirroring `AlbumNavTree.vue`'s existing usage of the same component (FR-063-15).
- Virtualize the album grid: a new `AlbumThumbGridVirtual.vue` under a new `resources/js/v8/components/gallery/albumModule/Virtualized/` directory (kept separate from the existing flag-off components so this feature's components can be deleted as a unit if the approach changes or v2 is later retired), a single virtualizer instance over a flattened row list (one row per bucket header, one row per `itemsPerRow`-wide slice of tiles). Uses `@tanstack/vue-virtual` the same `translate3d`-positioned-rows-over-a-single-relative-spacer pattern `AlbumNavTree.vue` established, but `useWindowVirtualizer` (with a reactive `scrollMargin` tracking this component's own document-relative top offset) rather than `AlbumNavTree.vue`'s `useVirtualizer`-against-its-own-scroll-box: `AlbumNavTree.vue` scrolls inside its own fixed-height sidebar, whereas `AlbumPanel.vue`'s content (`AlbumHero`, this grid, `PhotoThumbPanel`, ...) shares one ordinary page/window scroll (`#galleryView` carries no `overflow-y`/bounded-height styling in v8, unlike v7's equivalent). Items-per-row and tile width are computed analytically by a new `useAlbumTileWidth()` composable (`resources/js/v8/composables/album/albumTileWidth.ts`) — container width via `useElementSize()` on the grid's own root, current Tailwind breakpoint via `useBreakpoints(breakpointsTailwind)` (both `@vueuse/core`, already used elsewhere in this codebase), tile width from the same `calc()` formula already encoded in each breakpoint's CSS class — no mounted probe tile, and no reuse of the unrelated photo-layout `getWidth.ts` helper (a different, imperative, scrollbar-guessing measurement built for justified/masonry layouts). `3xl`/`4xl` are deliberately not modeled: confirmed via the actual compiled production CSS that this project defines no `--breakpoint-3xl`/`--breakpoint-4xl`, so Tailwind v4 silently drops every `3xl:`/`4xl:`-prefixed utility at build time (including `AlbumThumb.vue`'s own), making `2xl`'s formula the one that already applies at `2xl` and beyond. Each tile row's height is then computed analytically as `tileWidth ÷ aspectRatioNumber`, using the parent album's own `album_thumb_css_aspect_ratio` (already available on the loaded album via `AlbumConfig`/`RootConfig` — per-album override or instance default, the same value `AlbumThumb.vue` itself already applies via CSS) (FR-063-14). Bucket header rows render as an ordinary (non-sticky) part of the virtualized row list; a separate always-present overlay element, `position: sticky; top: var(--ui-header-height)` (docking below the page's own sticky top bar, the same variable `AlbumNavPanel.vue`'s sticky sidebar already uses), shows the current section's label once that section's own row has scrolled past the top — `position: sticky` does not apply to the translate3d-absolutely-positioned rows themselves, so the pinned label is this separate element, not the real header row going sticky.
- Virtualize the album list view (`album_view_mode === 'list'`) via a new `AlbumListViewVirtual.vue`, the same way, degenerately (one tile per row, `itemsPerRow = 1`, a fixed row height rather than the grid's aspect-ratio-derived one) — same flattened-row `useWindowVirtualizer` model, reusing the same row-building function, rendering a new `AlbumListItemVirtual.vue` per row (FR-063-17) that resolves its own cover image via `<Thumb>` the same way `AlbumThumbVirtual.vue` does, forked from `AlbumListItem.vue`. Both branches are dispatched by a small `AlbumThumbPanelVirtual.vue` wrapper (mirroring `AlbumThumbPanel.vue`'s own grid/list `album_view_mode` dispatch) that `AlbumPanel.vue` renders in place of `AlbumThumbPanel.vue`+`<Pagination>` when the flag is on.
- Fall back to a single, unbucketed windowed section (no sticky headers) when tier 1 reports `bucketable: false` — mirrors today's existing `isTimeline && buckets.length > 1` gate in `AlbumThumbPanel.vue`/`PhotoThumbPanel.vue`.
- Reimplement `resources/js/composables/album/dragAndSelect.ts`'s album-selection path against the same precomputed tile-geometry model the virtualizer already has to build (row/column → absolute box), instead of `document.querySelectorAll('[data-album-id]')` DOM traversal — the current implementation can only ever select currently-mounted tiles, which becomes actively wrong (not just incomplete) once most tiles are intentionally unmounted. Scoped to the album-grid path only when the flag is on; the v2/flag-off and photo-grid drag-select paths are untouched.
- Stop calling `AlbumState.ts`'s v2 `loadAlbums()`/`loadMoreAlbums()` and hide the albums `<Pagination>` control for the current album's subalbum section when the flag is on (there is nothing to paginate — tier 2 is whole-album-at-once); both remain fully intact and unchanged for the flag-off path.
- Re-fetch (not merely re-render) the joined tier 1+2 dataset after any mutation performed from within the currently-open album's subalbum section that changes what those endpoints would return — create, delete, move, rename (affects sort order/bucket), lock/unlock, visibility change, cover photo change (FR-063-13). No dedicated re-fetch method turned out to be needed: every one of those mutations already ends in `emits("refresh")`/`Album.vue`'s `refresh()`, which already calls `albumStore.refresh()` → `load()` → `loadAlbumsAuto()` → `loadAlbumsV3()` — the same cascade the v2 path already relies on for its own equivalent refresh. `AlbumService.clearCache()`'s existing call sites (already extended to clear the three new v3 cache-entry ids) keep that re-fetch from being served stale.
- Cache each `loadAlbumsV3()`/`getBuckets()`/`getChildren()`/`getRights()` request via this codebase's existing `axios-cache-interceptor` convention (`AlbumChildrenV3Service`, enumerable per-`album_id` cache ids), the same mechanism `AlbumService` already uses for v2 — not a separate Pinia-level cache (FR-063-19). Invalidated by the same `AlbumService.clearCache()` call sites FR-063-13 relies on — repeat navigation to a recently-browsed album renders from cache, not a fresh round-trip.
- Guard against stale cross-album responses: `loadAlbumsV3()`/`loadAlbumsV3Rights()` capture `this.albumId` as `requestedAlbumId` at call time and compare it back before applying a response — the same `requestedAlbumId`-capture-and-compare pattern `loadHead()`/`loadAlbums()`/`loadPhotos()`/`load()` already use elsewhere in `AlbumState.ts`, reused as-is rather than adding a new generation-counter mechanism (FR-063-18).
- **(2026-09-02 addendum)** Root gallery's Smart Albums section (`Albums.vue`) sources its `baseSmartAlbums` from `GET /Albums/smart` (Feature 062) instead of v2's `Top::get()` when the flag is on, via a new `AlbumsState.ts` action `loadSmartAlbumsV3()` and a new `resources/js/v8/utils/adaptSmartAlbumTile.ts` adapter reusing FR-063-06's `AdaptedAlbumTile` type (FR-063-20/21). `AlbumThumbImage.vue` gains a small additive branch — a `coverId`/`albumId` prop pair resolved via `<Thumb>`/the Feature 056 Asset endpoint when `thumb` is absent, otherwise fully unchanged — so v3-sourced smart tiles and still-v2-sourced tag/person tiles keep rendering side by side in the same `<AlbumThumbPanel>` call, with zero change to `Albums.vue`'s template (FR-063-22). Feature 062's `AlbumCategoryController::smart()` and Feature 056's `GetPhotoAssetRequest` are amended (FR-062-16, FR-056-08) so this addendum ships with real cover pixels, not a generic-icon regression (Q-063-15).

## Non-Goals

- **No photo-level virtual scrolling.** Scoped entirely to the subalbum (children) section of `AlbumPanel.vue`. Photo grid virtualization (justified/masonry/grid layouts) is deferred to a later feature per `virtual-scrolling-study.md`'s own phased recommendation ("Albums first... Photos... last").
- ~~No root-scope (top-level gallery / `Albums.vue`) virtualization or bucketing.~~ **(2026-09-02, superseded by the full-scope addendum, Q-063-16)** This was true when Feature 063 only consumed Feature 061's sub-album-children endpoints (061 explicitly excluded `Actions\Albums\Top::queryRootAlbums()` from tier 1). It is no longer this feature's boundary: `GET /Albums/root[/buckets|/rights]` (Feature 062) gives root the same tier1/2/3 bucket shape sub-album children already have, and this addendum's own/shared root grid (FR-063-24) virtualizes/buckets it the same way. Retained here, struck through, as a record of the original (now-superseded) scope decision rather than silently deleted.
- **(2026-09-02 addendum, superseded by Q-063-16) ~~No adoption of Feature 062's other four category/root endpoints~~.** Originally scoped to `/Albums/smart` only (Q-063-14). Superseded once the user clarified the actual intent was full root-gallery SoA adoption (Q-063-16) — all five of Feature 062's endpoints are now adopted (FR-063-20/21/24/25/26/27).
- **No changes to Feature 061's contract beyond FR-061-27 (`is_pinned`/`is_public`/`is_link_required` on tier 2).** This feature otherwise consumes the three endpoints exactly as they now stand; if a further gap is found, it is fixed in 061's spec, not worked around here.
- **No client-side sorting or grouping of tier 2's rows.** Tier 2 already arrives ordered to match tier 1's bucket boundaries (FR-061-26) — a client-side sort/group step here would be dead code duplicating a guarantee the backend already provides.
- **No v2 backend removal, deprecation, or modification.** `AlbumChildrenController`, `GetAlbumChildrenRequest`, `AlbumRepository::getChildrenPaginated()` are untouched and remain the flag-off path, exactly matching Feature 058's NFR-058-01 precedent. "Stop calling v2" (061 plan.md Follow-ups) means the frontend stops calling it *when the flag is on* — not that the route is deleted.
- **No change to `AlbumState.ts`'s photo pagination/timeline logic**, `PhotoThumbPanel.vue`, `splitter.ts`'s photo-side usage, or any photo-selection/drag-select path. Only the album-grid drag-select path is touched, and only when the flag is on.
- **No fix to `dragAndSelect.ts`'s photo-selection geometry lookup or any other consumer of its DOM-query helpers.** Only the album-selection branch is reimplemented against precomputed geometry (Goals); the shared module's photo-selection code path, and its exported DOM-query helpers used elsewhere, are left exactly as-is.
- **No new feature flag.** Reuses `modules.is_struct_of_array_enabled` as-is, consistent with Feature 058's Q-058-02/03 resolution (one combined flag, generically named).
- **No automated frontend test suite.** This repo has none (confirmed Feature 049, reaffirmed Feature 058); verification is manual/browser-based, per Feature 058's precedent.
- **No visual redesign of tile appearance beyond what tier 2's leaner data forces.** Badges, decorations, selection outline, and layout render identically to today; what changes is which tiles are mounted at any moment, that bucket section headers become sticky (a deliberate, called-out addition, not incidental), and the two accepted regressions below.
- **No video play-icon overlay or blur-up placeholder fade-in for flag-on tiles.** Both existed in `AlbumThumbImage.vue` via `thumb.type`/`thumb.placeholder`, which Feature 061 deliberately excluded from tier 2 (Non-Goals: "requires a join to `photos`/size-variant rows to resolve — incompatible with this endpoint's single flat query goal"). `AlbumThumbVirtual.vue` (FR-063-15) still reproduces the *other* fallback `AlbumThumbImage.vue` computes from data tier 2 does supply — a password icon when `cover_id` is `null` and `is_password_required` is `true`, a generic no-image icon otherwise — since that only needs `cover_id`/`is_password_required`, both present on every tier 2 child. Flag-off tiles are completely unaffected (`AlbumThumb.vue`/`AlbumThumbImage.vue` untouched).
- **No windowed/paginated variant of tier 2 introduced on the frontend.** Consumes `GET .../children` exactly as 061 ships it — one whole-album-at-once fetch per album navigation. If that payload ever proves too large in practice, 061's own Follow-ups already earmarks a `bucket_id` query-param extension to that endpoint as the fix; this feature does not preempt that.
- **v8 only — no v7 changes**, consistent with every prior struct-of-array feature (057/058/061). `resources/js/v7/...`'s independent, unwindowed subalbum rendering and its own `AlbumService.clearCache()` calls are untouched.
- **No change to `AlbumThumb.vue`/`AlbumThumbImage.vue` themselves, and no change to how the flag-off subalbum grid resolves a cover image.** They remain exactly as they are today (pre-built URL strings from v2's embedded `ThumbResource`) — only the new flag-on `AlbumThumbVirtual.vue` (FR-063-15) uses the Feature 056 Asset endpoint, because tier 2 gives it no other way to get pixels.
- **No change to `Thumb.vue`, `ThumbAssetService`, or the Feature 056 Asset endpoint itself.** All three already exist and are already used elsewhere (`AlbumNavTree.vue`, `SearchTargetAlbum.vue`, `SpotlightSearch.vue`) — this feature is a new consumer, not a modification.

## UI / Interaction Mock-ups

## Appendix

### Decision Cards (Q-063-01..04)

#### Q-063-01 — Where the tier 1+2 fetch/boundary logic lives

**Resolved:** the adapted tiles are written into the existing `resources/js/stores/AlbumsState.ts` (the store already backing `AlbumPanel.vue`'s subalbum section, holding `albums: ThumbAlbumResource[]`) rather than a parallel store, so the flag-on and flag-off paths both populate the exact same store field with the exact same shape (FR-063-06) — the lowest-blast-radius way to keep `AlbumThumb.vue`/`contextMenu.ts` unaware which path fed them. The tier 1/2/3 fetch logic and derived bucket state itself (`bucketsV3`/`boundariesV3`/`bucketableV3`/`loadAlbumsV3()`) instead extends `resources/js/stores/AlbumState.ts` (singular) — the store `config`/`rights`/the v2 `loadAlbums()` already live on — since that data is per-currently-browsed-album navigation state, not the cross-component `.albums` array itself; discovered during implementation that these are two different existing stores, not one. Mirrors Feature 058's Q-058-04 reasoning (shared state, existing store family) but scoped to the already-relevant per-album stores rather than a new session-wide one. The store's boundary-derivation job is a positional walk over tier 1's `counts` (FR-063-02) — not a join or sort, since tier 2 already arrives ordered to match tier 1's bucket boundaries (FR-061-26).

#### Q-063-02 — Grid virtualization technique

**Resolved:** a single `useVirtualizer` instance over a flattened row list (bucket header rows interleaved with N-tile rows), following `AlbumNavTree.vue`'s single-column `useVirtualizer` pattern as a general reference for a multi-column grid with sticky section headers and aspect-ratio-driven row heights — rather than hand-rolling a binary-search-over-precomputed-boxes composable from scratch (the approach `virtual-scrolling-study.md` sketches for the harder justified-photo-layout case). `@tanstack/vue-virtual` is already a **direct** dependency (confirmed in `package.json`, not merely transitive as `virtual-scrolling-study.md` originally noted before this package was later added directly) and already has one real usage in this exact codebase to draw general conventions from (`translate3d` positioning, single absolutely-positioned spacer sized to `getTotalSize()`, `contain: strict`/`layout size paint`) — not a template whose internals this feature must replicate exactly, since the array/row model here (multi-column, sticky headers, analytically-computed row heights) differs enough from `AlbumNavTree.vue`'s single-column tree to justify its own structure. The flattened-row-with-sticky-header-rows approach is `@tanstack/vue-virtual`'s own documented pattern for sticky section headers, not a bespoke technique.

New components for this feature (DO-063-03/04, plus any supporting sub-components split out during implementation — e.g. a bucket-header-row or tile-row component) live under a new `resources/js/v8/components/gallery/albumModule/Virtualized/` directory, physically separate from the existing flag-off components, so they can be deleted as a unit if the approach changes or v2 is eventually retired.

#### Q-063-03 — Fixing vs. documenting the `dragAndSelect.ts` DOM-query gap

**Resolved:** fixed, not merely documented as a degradation (FR-063-11) — the geometry a virtualizer needs to compute (row/column → absolute box for every child, not just mounted ones) is already the exact input `dragAndSelect.ts`'s album-selection branch needs to test rectangle-intersection against, so reusing it turns a would-be regression into a strict improvement over today's DOM-query approach (which already silently only worked for the fully-mounted case, before this feature ever introduces partial mounting). Scoped narrowly: only the album-selection branch, only when the flag is on and the active panel is virtualized — the photo-selection branch and the flag-off album branch are both left exactly as they are today (Non-Goals).

#### Q-063-04 — How the virtualized grid resolves each tile's cover image

**Resolved:** a new `AlbumThumbVirtual.vue` (FR-063-15), forked from `AlbumThumb.vue`, using `<Thumb :album-id :photo-id type="thumb">` (`resources/js/v8/components/thumbs/Thumb.vue`) instead of `AlbumThumbImage.vue` — not a reuse-`AlbumThumb.vue`-unchanged approach. This was forced by the data, not a preference: tier 2 (`GET .../children`) supplies only `cover_id`, deliberately (Feature 061 Non-Goals) omitting the pre-built thumbnail URL/`type`/`placeholder` that `AlbumThumbImage.vue` requires — that pairing simply cannot render tier 2 data as-is. `Thumb.vue`/`ThumbAssetService`/the Feature 056 Asset endpoint already exist and are already used for exactly this per-item, ID-in-props-out-object-URL pattern by `AlbumNavTree.vue` (itself an already-virtualized single-column tree) — reusing that precedent is a strict improvement over inventing a second image-loading mechanism, and it composes naturally with virtualization: an asset is only ever requested once its tile actually mounts, and `Thumb.vue`'s existing `onBeforeUnmount`/`release()` means an off-screen tile's blob URL is freed automatically, with no new lifecycle code this feature has to write.

Accepted trade-off: tier 2's leaner shape means `AlbumThumbVirtual.vue` cannot reproduce `AlbumThumbImage.vue`'s video-play-icon overlay or blur-up placeholder fade-in (both need `thumb.type`/`thumb.placeholder`, which Feature 061 excluded from tier 2 on purpose). The no-cover fallback (password icon vs. generic no-image icon) *is* reproduced, since it only needs `cover_id`/`is_password_required`, both present on every tier 2 child. Flag-off tiles (`AlbumThumb.vue`) are entirely unaffected either way.
