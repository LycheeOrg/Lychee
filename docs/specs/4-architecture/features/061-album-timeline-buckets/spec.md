## Overview

Backend-only foundation for virtual-scrolling an album's direct children (subalbums). Three new `GET` endpoints, all scoped to one parent `album_id`, all backend-contract-only (no frontend consumer in this feature):

- **`GET /api/v3/Albums/{album_id}/children/buckets`** — returns `{bucket_id, count}` pairs for an album's direct children, grouped by whichever date source would currently label them (`created_at`, `min_taken_at`, `max_taken_at`, or a parsed leading date in `title`), plus a ready-to-render display label per bucket. Lets a client render sticky date headers and size a scrollbar before fetching any child-album rows.
- **`GET /api/v3/Albums/{album_id}/children`** — returns the actual per-direct-child data (`id`, `title`, `description`, `cover_id`, `bucket_id`, flags, counts, dates) needed to render a tile, as one whole-album-at-once Struct-of-Arrays response. Each child's `bucket_id` is the join key back to the buckets endpoint's `{bucket_ids, counts}` — a client groups this endpoint's children by `bucket_id` to know which sticky-header section each tile belongs under.
- **`GET /api/v3/Albums/{album_id}/children/rights`** — returns the permission signals a right-click context menu (single- or multi-select) needs to decide what actions to offer, for every direct child at once. Meant to be fetched by the client in the background immediately after the children endpoint renders, not on the right-click/selection event itself — a context menu needs this data with zero interaction-time latency, and per-child permission computation is too expensive to fold into the children endpoint's own response.
- **Cover pixels** are already served by Feature 056's `GET /api/v3/Asset/{album_id}/{photo_id}/{size_variant}`, fired per mounted tile by the browser once the children endpoint supplies each child's `cover_id` — no new endpoint needed for that.

At the confirmed real-world scale of a single parent with 7,000+ direct children, computing bucket aggregation by loading rows into Eloquent and grouping in PHP would hydrate the server into the ground, and a live `GROUP BY DATE_FORMAT(...)` in SQL is itself expensive at that row count (per-row function evaluation defeats a plain index on the `GROUP BY` key). The fix: a new **materialized, pre-truncated `bucket_id` column** on `albums`, composite-indexed with `parent_id`, so the buckets endpoint's query is always a plain, cheap, indexed `GROUP BY bucket_id` — never a function evaluation, never row hydration. `bucket_id` is a single column (not one per date source): a parent's sort column and timeline granularity are both persisted, single, shared settings on that parent row, not a per-viewer or per-request choice — so at any moment there is exactly one canonical date source and one canonical granularity relevant to a given parent's children, and each child needs exactly one `bucket_id` value.

All three endpoints are gated behind the existing `STRUCT_OF_ARRAY_ENABLED` flag (Feature 058's flag) — no new flag is introduced. Together they are intended to eventually replace `AlbumChildrenController`'s v2 paginated children listing entirely; a separate frontend-adoption feature (mirroring Feature 058) is required before that listing can actually be retired, since this feature ships backend contracts only.

## Goals

- Add one nullable `string` column, `bucket_id`, to `albums` — holding the already-truncated date-bucket label (e.g. `"2024-03"`, `Y`/`Y-m`/`Y-m-d` format) for whichever date source and granularity are currently in effect for that album's own parent; **or**, when the parent is sorted by `TITLE` and the instance-wide `title_bucket_mode` config is `alphabetical`, an alphabetical prefix of the child's own `title_base`. When the parent is sorted by `OWNER_ID`, `bucket_id` is always `null` and never computed — every direct child of a given album always shares that album's exact `owner_id` (album creation/move/merge/transfer all force this), so grouping by `OWNER_ID` can never produce more than one bucket, and it is excluded from bucketing entirely. `NULL` also occurs under `date_prefix`-mode `TITLE` (no parseable leading date) and under `MIN_TAKEN_AT`/`MAX_TAKEN_AT` (no dated photos anywhere in the child's subtree — both columns are themselves nullable) — `CREATED_AT` and `alphabetical`-mode `TITLE` are the only never-null bucketable sources.
- Add one composite index `(parent_id, bucket_id)`, so the buckets endpoint's `GROUP BY` is index-served with zero per-row function evaluation.
- Provide `GET /api/v3/Albums/{album_id}/children/buckets`, scoped to one parent album's **direct children** (same scoping/visibility filter as `AlbumRepository::queryChildrenPaginated()`), returning a Struct-of-Arrays `{bucket_ids: string[], counts: int[], labels: string[], bucketable: bool}` body per ADR-0009, ordered to match the parent's own sort direction. `labels[i]` is a ready-to-render display string for `bucket_ids[i]`, computed at read time (not materialized) — this is what lets a client render sticky headers without any client-side date formatting.
- Group rows whose `bucket_id` is `NULL` into one explicit `"unknown"` sentinel entry in the response — never silently dropped.
- Populate `bucket_id` at write time, piggybacked onto the existing `RecomputeAlbumStatsJob` (already dispatched on every relevant Album mutation — save, move, photo add/remove, delete-with-parent), by reading the album's own parent's resolved sort column and granularity, not a fixed source or a global constant.
- Handle the two write-time triggers `RecomputeAlbumStatsJob` does not already cover: when an album's own `album_sorting_col`/`album_sorting_order` **or** `album_timeline` changes, its **direct children's** `bucket_id` column (not its own) needs recomputing, since both settings are resolved from the parent, not the child.
- Provide a console command to bulk-recompute every album's `bucket_id` column from data already on that row plus its parent's settings (initial backfill at deploy time, and re-run if an instance-wide `sorting_albums_col`/`timeline_albums_granularity`/`title_bucket_mode`/`title_bucket_prefix_length` default changes).
- Make `TITLE`-sort bucketing itself configurable, instance-wide only: `title_bucket_mode = date_prefix` (default — parse a leading date out of `title`) or `title_bucket_mode = alphabetical` (bucket = first `title_bucket_prefix_length` characters of `title_base`, the same value `TITLE` sort actually orders by — the only mode that gives `bucket_id` boundaries the chunking/contiguity property `CREATED_AT`/`MIN_TAKEN_AT`/`MAX_TAKEN_AT` already have).
- Gate all three endpoints behind `modules.is_struct_of_array_enabled` — no new flag.
- Reuse `AlbumQueryPolicy::applyVisibilityFilter()` and `ManagedCacheService`/`CacheKeyProvider`, tagged so all three endpoints' caches are invalidated by the exact same events that already invalidate `AlbumRepository::getChildrenPaginated()`'s cache — no new invalidation listener wiring for the buckets/children endpoints (the rights endpoint's cache additionally needs to react to permission changes, a distinct concern — see FR-061-22).
- Provide `GET /api/v3/Albums/{album_id}/children`, scoped to one parent album's **direct children**, returning a Struct-of-Arrays body with the minimum fields an album tile actually renders plus each child's own `bucket_id` — `id`, `title`, `description` (SQL-truncated to 100 chars), `cover_id`, `bucket_id` (`"unknown"` for `null` — the join key back to the buckets endpoint), `is_password_required`, `is_nsfw`, `has_subalbum`, `num_photos`, `num_subalbums`, `created_at`, `min_taken_at`, `max_taken_at` — as one flat `toBase()` query with zero additional joins beyond the visibility-policy baseline, whole-album-at-once (no windowed pagination).
- `cover_id` only — no thumbnail URL, no media `type`, no blur `placeholder`. Resolving `cover_id` to actual pixels (and media type, if a client wants it) is the caller's job via the existing Feature 056 Asset endpoint.
- Provide `GET /api/v3/Albums/{album_id}/children/rights`, scoped to one parent album's **direct children**, returning the raw permission signals a right-click menu on a selection of albums needs — not the fully-combined `can_*` booleans — with zero query at interaction time: one whole-response `owner_id` (uniform across all direct children, lets the client derive every owner-based right client-side against its own already-known user identity); one whole-response `can_delete_children`/`can_move_children` pair (also uniform — both check grants on the *parent's* `access_permissions`, keyed by `parent_id`, which is `album_id` itself for every direct child); and two per-child Struct-of-Arrays fields — `grants_edit`, `grants_download` — the only rights components that genuinely vary per child (a subalbum can be individually shared independent of its siblings) and are actually offered by that menu. `grants_upload`/`grants_full_photo_access` are not transmitted, since neither underlying right is offered by that menu at all.
- Compute the two per-child grant arrays via one `LEFT JOIN` against `AlbumQueryPolicy::getComputedAccessPermissionSubQuery(full: true, user: $currentUser)` (Feature 057's existing bulk-permission mechanism, reused with the real caller instead of the `null`/public-only case its one current call site uses) — `MAX()`-aggregated per child to correctly collapse the case where a caller's multiple group memberships each grant a matching row for the same child (the subquery applies no `GROUP BY` in `full: true` mode, so a naive join would emit duplicate/inconsistent rows). Admins short-circuit to every grant `true` without the join ever running, replicating the same early-return `applyVisibilityFilter()` already does elsewhere for admins.

## Non-Goals

- **No frontend work.** No v8 component, composable, or store consumes any of the three endpoints in this feature. A future adoption feature wires sticky headers, virtual-scroll windowing, background rights-prefetching, and the client-side owner/grant-combination logic.
- **No root-scope (`album_id` omitted) bucketing.** The root album listing (`Actions\Albums\Top::queryRootAlbums()`) is a materially different query shape — `whereIsRoot()`, ownership-partitioned, mixed with smart/tag/person albums that have no bucket-relevant date columns at all. This feature covers only drilling into any album's own subalbums, at any depth, never the top-level gallery landing page.
- **No photo-side bucket column/endpoint.** `Photo.taken_at`/`created_at` bucketing is left for a later phase.
- **No change to `Timeline.php::dates()`** (the existing live-`DATE_FORMAT` photo-timeline query) or to `TimelineData::fromAlbum`/`setTimeLineDataForAlbums` — both are left exactly as-is.
- **No removal or modification of `AlbumChildrenController`/`GetAlbumChildrenRequest`/`AlbumRepository::getChildrenPaginated()`.** This feature ships the full backend replacement (all three endpoints) alongside the still-fully-functional v2 path, unmodified; a frontend-adoption feature still has to wire it all up and stop calling v2 before v2 can actually be removed.
- **No tier-3 (pixel) endpoint.** Already served by Feature 056's Asset endpoint, unchanged — the children endpoint supplies the `cover_id` that fetch needs, nothing more is required here.
- **`bucket_id` itself stays a raw, unformatted grouping key on both the buckets and children endpoints.** The buckets endpoint's `labels` array is a separate, additional field, not a reinterpretation of `bucket_id` — display formatting for date-based buckets reuses the same mechanism `TimelineData::fromAlbum` already uses (Carbon `->format()` against the instance-wide `timeline_album_date_format_*` config keys), not a per-viewer locale (this codebase has no such concept). The children endpoint never carries a label at all — a label is only meaningful once per distinct bucket, which the buckets endpoint's aggregate response already represents; repeating it once per child row would be pure waste.
- **No thumbnail media `type` or blur `placeholder` on the children endpoint.** Both existed on v2's `ThumbAlbumResource`/`ThumbResource` but require a join to `photos`/size-variant rows to resolve — incompatible with this endpoint's single flat query goal (zero additional joins beyond the visibility-policy baseline). The video badge and blur-up placeholder are not reproduced by this feature at all.
- **No change to `album_timeline`'s existing `DEFAULT`/`DISABLED` resolution quirk.** `HasTimelineData::getAlbumTimeline()` currently resolves both `DEFAULT` and `DISABLED` to the instance-wide default. This feature's `bucket_id` population reuses that exact existing resolution function unchanged.
- **No TagAlbum/PersonAlbum bucketing (tier 1 only).** Those models have no `min_taken_at`/`max_taken_at`/`bucket_id` columns and are not scoped by `parent_id` the way regular `Album` rows are; the buckets endpoint only ever queries the regular `albums` table (`GetAlbumBucketsRequest` resolves a regular `Album` only, 404 for `TagAlbum`/`PersonAlbum`). **Amendment (2026-08-29, post-implementation follow-up):** tiers 2 (`GET .../children`) and 3 (`GET .../children/rights`) *do* support `TagAlbum`/`PersonAlbum` — see FR-061-24/25 below. Only tier 1 stays regular-`Album`-only: a materialized `bucket_id` has no single governing sort column/granularity to group by for a dynamically-matched, disparately-parented "matching albums" result set.
- **No new feature flag.** Reuses `STRUCT_OF_ARRAY_ENABLED`/`modules.is_struct_of_array_enabled` as-is.
- **No dependency on `SortingDecorator`'s row-ordering semantics.** `SortingDecorator` sorts every column purely in SQL; this feature's bucket-list ordering is a plain `ORDER BY bucket_id <dir>`, since a date-bucket string has no relationship to a title's SQL sort order.
- **No bucketing by `RATING_AVG`/`IS_HIGHLIGHTED`/`TYPE`.** Photo-only columns that do not exist on `albums`/`base_albums`, gated out of `sorting_albums_col`/`album_sorting_col` entirely by `ColumnSortingAlbumType` — they cannot occur as an album's effective sort column through any current write path. Nothing to bucket.
- **No bucketing by `OWNER_ID`.** A valid `ColumnSortingAlbumType` value and a real, reachable effective sort column for a parent album — but excluded from the bucketable set for a structural reason: every direct child of a given `album_id` always shares that album's exact `owner_id` (`Actions\Album\Create::set_parent()`/`Move`/`Merge`/`Transfer` all force this). Grouping a set that is, by construction, always single-valued can never produce more than one bucket. `OWNER_ID` remains a fully valid choice for `album_sorting_col`/`sorting_albums_col` itself — only its bucketability is affected.
- **The rights endpoint is scoped to "core menu rights," not full `AlbumRightsResource` parity.** `can_make_purchasable` (multiple config/feature-flag/license checks) and `can_import_from_server` (global, not per-album) are excluded — neither is a per-album right-click concern. The AI-vision face-permission fields are excluded too — separately feature-flagged, a different feature's concern. `can_upload`/`can_access_original` are excluded — neither action is offered by the right-click menu on a selection of albums, so their per-child grant components (`grants_upload`/`grants_full_photo_access`) are not transmitted at all. Covered: `can_edit`, `can_download` (their per-child, `access_permissions`-grant component only), `can_delete`, `can_move`, `can_transfer`, `can_share`, `can_share_with_users` (the latter three, plus the owner-based component of the first two, are never transmitted — they reduce to zero-cost client-side computation off `owner_id` and the caller's own already-known identity).
- **The rights endpoint returns raw grant signals, not the final combined `can_edit`/`can_download` booleans.** `AlbumPolicy`'s actual logic for each is `(isOwner && possibly-more) OR grants_*`; the client already knows its own identity and `may_upload` flag for free, so combining `owner_id === current_user_id` (and `may_upload`, where relevant) with the transmitted `grants_*` flag is a small, well-defined client computation — deliberately not replicated server-side, and out of scope here regardless (see "No frontend work").
