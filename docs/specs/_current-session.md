### Feature 053 – Album Listing Caching — Spec/Plan/Tasks drafted (this session, 2026-08-08)

**Request:** Add caching support for sub-album/album listings, building on Feature 052's `ManagedCacheService`. Explicit requirement: find every place in the codebase that would need a cache refresh, and use proper domain events dispatched at mutation sites — not Eloquent model observers, since many mutations bypass Eloquent's event system entirely (raw `DB::table()`, bulk `Model::query()->update()`, pivot `attach()`/`detach()`, vendor nested-set internals).

**Audit (self + one background `general-purpose` agent, resumed once after an API error mid-run):** confirmed Feature 052's own superseded design correctly identified 3 gaps (`Move`, `SharingController`, `UserGroupsManagementController`) but found roughly a dozen more, including: `AlbumController::updateAlbum()`/`updateTagAlbum()`/`updatePersonAlbum()`/`cover()`/`header()`/`updateAlbumHeader()`/`rename()`/`setPinned()` (the most common album-edit endpoints) dispatch no domain event at all; `Actions\Admin\BulkEditAlbumsAction` mass-updates `albums`/`base_albums` columns via raw query-builder `->update()` with zero events (including an `is_nsfw`-only bulk edit that Group 3's visibility-event branch silently excludes); `Album::fixOwnershipOfChildren()` bulk-updates `owner_id` for an entire subtree in one raw query; `Transfer::do()` dispatches nothing; deleting a photo can silently blank a *different* album's `cover_id`/`header_id` anywhere in the instance (raw, unscoped bulk update in `PhotosToBeDeletedDTO`); `RecomputeAlbumStatsJob`/`RecomputeAlbumSizeJob` write the actual displayed stats/cover *after* their triggering event, with no completion signal; the global default sort config (`sorting_albums_col`/`order`) has no album row to hook at all; and a **pre-existing latent bug** was found — `SetProtectionPolicy::do(BaseAlbum $album, ...)` unconditionally calls `AlbumSaved::dispatch($album)`, but `AlbumSaved`'s constructor is typed `Album`, so setting protection policy on a `TagAlbum`/`PersonAlbum` throws a `TypeError` at runtime today; fixing it became in-scope (FR-053-11) since Feature 053 needs `TagAlbum`/`PersonAlbum` protection changes to correctly invalidate the newly-in-scope root listing.

**6 open questions logged and resolved same-day, all via direct user choice (not silently defaulted), Q-053-01..06:**
- Q-053-01: scope — **both** the sub-album (children) listing and the more complex root-level `Actions\Albums\Top` view (smart/tag/person/pinned/root albums) are in scope (user chose the broader option over the recommended children-only scope, matching Feature 052's original pilot).
- Q-053-02: photo-listing caching (`PhotoRepository::getPhotosForAlbumPaginated()`) explicitly deferred to a future feature.
- Q-053-03: reuse Feature 052's `managed_cache_enabled`/`managed_cache_ttl` (never migrated) rather than a new dedicated flag — this feature finally ships that migration (Feature 052's deferred T-052-05/06, now `T-053-01`).
- Q-053-04: async recompute-job completion (`RecomputeAlbumStatsJob`/`RecomputeAlbumSizeJob`) also triggers cache eviction, via a new `AlbumComputedDataUpdated` event consumed only by the new cache listener (not by the existing recompute-triggering listeners, to avoid a dispatch loop).
- Q-053-05: the global sort-config gap is closed by a deliberately coarse, instance-wide cache flush (new `AlbumListingCacheFlushRequested` event) rather than never caching override-less albums (which would gut most of the caching benefit, since overrides are rare).
- Q-053-06: the cross-album photo-delete cover/header gap is fixed (not left uncovered) — `PhotosToBeDeletedDTO` now captures affected album ids before the raw nulling update and dispatches per affected album.

**Design shape (spec.md's Interface & Contract Catalogue):** 4-tag scheme (`album:{id}`, `album-children:{parent_id|'root'}`, `user:{id}`, `album-listing-global` for the 5 deliberately-coarse triggers), 8 new events (`AlbumChildrenChanged`, `TagAlbumSaved`, `PersonAlbumSaved`, `BaseAlbumRemoved`, `AccessPermissionChanged`, `UserGroupMembershipChanged`, `AlbumComputedDataUpdated`, `AlbumListingCacheFlushRequested`), 2 new listeners (`ManagedCacheAlbumListingInvalidator`, `ManagedCacheUserListingInvalidator`), 24 FRs across 6 groups (cache adoption; album-tree mutations; tag/person album events; permissions/group membership; async/coarse triggers; listeners/tag scheme), 6 NFRs, 27 scenarios. `AccessPermissionChanged`/`UserGroupMembershipChanged` resurrect Feature 052's designed-but-never-implemented events of the same name.

**Plan shape:** 18 increments (I1–I18), ordered: config migration prerequisite → event scaffolding → per-mutation-site dispatch wiring (13 increments, each with its own failing test first) → listeners + `EventServiceProvider` registration → cache adoption in both consumers → full regression/drift-gate/docs. `tasks.md` mirrors this as T-053-01..22.

**Post-draft correction #1 (same session, user review):** the first spec draft folded `is_pinned` changes into the coarse instance-wide flush, but no dispatch site actually triggered that flush for a plain pin/unpin — `setPinned()`/`updateAlbum()` only dispatch `AlbumSaved`, which only evicted the album's *actual* parent, not `Top()`'s cross-tree `pinned_albums` section (not `parent_id`-filtered, can include deeply-nested albums). User caught this and asked for root + actual-parent listings to both refresh on pinned actions (Q-053-07). Fixed by giving `AlbumSaved`/`AlbumDeleted`/`AlbumChildrenChanged` a standing rule to always additionally evict `album-children:root` for regular albums — precise (two named tags), not a 6th coarse-flush trigger. `is_pinned` removed from the Non-Goals "no fine-grained tagging" bucket accordingly; new S-053-28.

**Post-draft addition #2 (same session, user request, Q-053-08):** user asked for a toggle to disable album-listing caching specifically, independent of the master `managed_cache_enabled` switch reused per Q-053-03. Added new config key `managed_cache_albums_enabled` (`BOOL`, default `'1'`, same `'Mod Cache'` category/migration/`SettingsController` exemption as T-053-01) plus a new `ManagedCacheService::rememberIf(bool $condition, ...)` method (small additive change to Feature 052's already-shipped service — condition false skips all cache I/O, condition true delegates to the existing `remember()` unchanged) so both switches AND together, neither overriding the other. New FR-053-25, SVC-053-03, S-053-29/30; FR-053-01/02 and Goal/Non-Goals text updated to reflect this is one hardcoded toggle, not an implementation of Feature 052's still-undesigned generic per-part-toggle Goal 4.

**Post-draft addition #3 (same session, user question, Q-053-09):** user asked whether albums-with-tags being shown in "tag albums" would stay correct under the new caching. Investigation found this actually refers to the Tag detail page (`GET /api/v2/Tag` → `GetTagWithPhotosAndAlbums`, distinct from the `TagAlbum` smart-album type already in scope), which shows both photos and regular `Album`s carrying a tag — not cached at all today, and not one of the two consumers already designed. User's answer added it as a third consumer, but corrected the framing: **cache at the SQL-query layer, not the request/response layer** — so only the action's `getAccessibleAlbums()` query is cached, its sibling `getAccessiblePhotos()` stays live (same rationale as the photo-listing Non-Goal). Investigating this surfaced a real design subtlety: `getAccessibleAlbums()` filters via `applyBrowsabilityFilter()`, which (unlike the other two consumers' `applyVisibilityFilter()`) additionally depends on session-scoped `AlbumPolicy::getUnlockedAlbumIDs()` — a naive user-id-only cache key would leak a password-protected album's presence across sessions. Closed via the cache-key design itself (include a hash of the unlocked-album set, so unlocking transparently produces a cache miss) rather than an eviction event — new NFR-053-07. Also found, while auditing this new area, that `EditTag`/`MergeTag`/`DeleteTag` mutate the `albums_tags` pivot via raw `DB::table()` with zero events (same class of gap as everything else in this feature) — closed via new event `AlbumTagsChanged` (mirrors the existing `PhotoTagsChanged`), dispatched from `updateAlbum()`'s tag sync, `MergeTag::handleAlbums()`, and `DeleteTag::do()`. New FR-053-26..31 (Section G), EV-053-11, SVC-053-04, tag `tag:{id}`, S-053-31..35; plan.md gained increments I16 (Tag CRUD wiring) and I19 (adoption), final wrap-up renumbered I20; tasks.md now T-053-01..24.

**Post-draft correction #4 (same session, user request, Q-053-10):** user asked to confirm the feature's caching focuses on SQL queries. Auditing against that principle found `Actions\Albums\Top::get()` (FR-053-02) had been specified as *one* monolithic cached unit despite internally running 4 independent queries (tag albums, person albums, pinned albums, root/shared albums) — the exact same "cache a whole multi-query action" anti-pattern already corrected for the Tag detail page in Q-053-09, just missed on `Top()` itself during that same pass. Fixed by splitting `Top::get()`'s caching into four independently-`rememberIf()`-wrapped queries, each with its own precise tag (`tag-albums-listing`, `person-albums-listing`, `pinned-albums-listing`, reusing `album-children:root` for the root/shared query); `Top::get()` itself is never wrapped, staying a plain assembler. `FR-053-22`'s listener mapping reworked accordingly (the old blanket "always evict `album-children:root`" rule split into targeted per-query rules). Valuable side effect: this exposed that `FR-053-17` (a coarse flush for smart-album protection changes) was entirely unnecessary all along — `Top()`'s smart-album section was never part of any cached query (always computed live via `Gate::check()`), so nothing was ever at risk of going stale; `FR-053-17` was removed (ID kept, struck, not renumbered, matching Feature 052's own convention for superseded requirements). Net effect: 20 mutation-site triggers (was 21), 4 coarse-flush triggers (was 5), 8-tag scheme (was 5), six independently-cached queries across three consumer actions (was three consumers with muddier boundaries). tasks.md count unchanged at 24 (T-053-15 repurposed to a regression test rather than removed, to avoid renumbering).

**Post-draft correction #5 (same session, user request — full consistency review, Q-053-11/12/13):** user asked for a dedicated pass over spec.md/plan.md/tasks.md looking for ambiguities, inconsistencies, and unknowns. Found one real, previously-unnoticed correctness bug (Q-053-11, High): `Top()`'s tag-albums, person-albums, and root/shared-albums sub-query cache keys (FR-053-02) were specified only as "user id + resolved sort criteria," but `app/Actions/Albums/Top.php` sorts all three by the *identical* `AlbumSortingCriterion::createDefault()` source — confirmed directly against the live code. Without a type-discriminating prefix, the three would generate textually identical cache keys for the same user, silently serving one query's cached data as another's. Fixed by giving each of the four sub-query keys an explicit type prefix matching its tag name, and adding a new NFR-053-08 with a dedicated key-uniqueness test. Also found and fixed: FR-053-01/02/26 never explicitly stated the `$ttl` argument's source (`managed_cache_ttl`, Q-053-12); and a batch of purely textual staleness (Q-053-13) — `SVC-053-02`/Domain Objects still described `Top::get()`/`TopAlbumDTO` as cached (contradicting the Q-053-10 fix), stale dispatch-site counts not accounting for `FR-053-17`'s removal, "both `getChildrenPaginated()` and `Top()`" language undercounting the now-six cached queries in several spots, and `tasks.md` using `F-053-` instead of this repo's established `FR-053-` ID prefix (~22 places) plus one malformed event-ID reference. All fixed directly (no design decision required); spec.md now includes NFR-053-08, so the NFR range bumped to NFR-053-01..08 throughout.

**Request:** Write plan.md/tasks.md for the already-spec-complete Feature 052, do a clarification pass, then implement.

**Implementation (all 22 tasks, T-052-01..22, ~30 new/changed files):**

- New events `AccessPermissionChanged`, `UserGroupMembershipChanged`; three previously-silent mutation points now dispatch: `Actions\Album\Move::do()` (also dispatches for the album's *previous* parent when it changed — needed for S-052-06 "both parents invalidated," not just the new one), `SharingController` (create/edit/delete/propagate), `UserGroupsManagementController` (addUser/removeUser/updateUserRole).

- Migration `2026_07_28_000001_managed_cache_config.php` (config rows) + `SettingsController` filter patch (Q-052-07).

**Two real correctness gaps found and fixed beyond the original spec text (not scope creep — both close testable Branch & Scenario Matrix rows already in spec.md):**
1. `Move::do()` originally only dispatched `AlbumSaved` for the moved album itself, which only carries its *post-move* (new) parent — the *old* parent's cached children-list would never be invalidated. Fixed by also dispatching `AlbumSaved` for the previous parent when it changed, mirroring the existing `Photo\MoveOrDuplicate` from/to dispatch pattern.
2. `ManagedCacheService::remember()`'s tags-up-front signature can't express "tag with the id of every item in the computed result" (needed for FR-052-09's per-child tagging). Added a small `addTags(key, tags)` method (no spec/contract change to `remember()` itself) to associate extra tags with an already-cached key after the callback has run.

**One spec self-consistency finding, no fix needed:** S-052-07 (ancestor-chain cascade, FR-052-08) is not actually exercised by FR-052-09/10's *normative* tag lists (parent + per-item tags only, no ancestor walk) — confirmed N/A for the two pilot consumers as specified, documented in plan.md's Scenario Tracking table rather than silently dropped.

**Testing:** ~35 new tests across `tests/Unit/Services/Cache/`, `tests/Unit/Listeners/`, `tests/Unit/Repositories/`, `tests/Feature_v2/Caching/` (new directory — real end-to-end wiring proofs with no faking), plus extensions to `AlbumMoveTest`, `SharingTest`, `UserGroupMembershipTest`, `GetAllSettingsTest`. ### Feature 052 (prior session, 2026-07-21) — Spec drafted and complete, all open questions resolved

**Request:** New feature to cache values whose result depends on the requesting user's access rights to one or more albums, with a dependency-mapping mechanism (album id + user id) so cached entries can be invalidated when access rights change, a photo is uploaded, an album is moved, etc.

**Existing infrastructure found (adjacent, not reused as-is):** `App\Metadata\Cache\RouteCacher`/`RouteCacheManager`/`App\Enum\CacheTag` already caches whole HTTP responses keyed by route+user, tagged by album id, with `AlbumCacheCleaner`/`TaggedRouteCacheCleaner` listeners reacting to `AlbumRouteCacheUpdated`/`TaggedRouteCacheUpdated`. Governed by `cache_enabled`, forced off by default since Feature 040 (`disable-request-caching`). Left untouched — this feature builds a new, independent, general-purpose service instead.

**Three real invalidation gaps confirmed during investigation (all fixed by this feature, FR-052-03/04/05):**
- `App\Actions\Album\Move::do()` (`app/Actions/Album/Move.php`) dispatches no event on album move/re-parent.
- `App\Http\Controllers\Gallery\SharingController` (`create`/`edit`/`delete`/`propagate`) dispatches no event when `AccessPermission` rows change.
- `App\Http\Controllers\Admin\UserGroupsManagementController` (`addUser`/`removeUser`/`updateUserRole`) dispatches no event on group-membership change.

**5 open questions logged and resolved same-day** (Q-052-01..05, all Option A):
- Q-052-01: generic service (not query-specific). **Pilot consumer changed 2026-07-21 (user instruction, post-resolution):** instead of `BaseAlbumImpl::current_user_permissions()`, the two pilots are `AlbumRepository::getChildrenPaginated()` (sub-albums) and `PhotoRepository::getPhotosForAlbumPaginated()` (photos) — both permission-filtered, hit on every album view, and the exact routes (`Album::albums`/`Album::photos`) the existing HTTP response cache already lists but runs uncached by default. No other adoption in this feature.
- Q-052-02: new independent `App\Services\Cache\ManagedCacheService` — user clarified it "does not necessarily have to be related to Query," driving the generic (not "query cache") naming/shape.
- Q-052-03: new independent config flag `managed_cache_enabled` (default `true`), decoupled from Feature 040's `cache_enabled`. New `managed_cache_ttl` config too.
- Q-052-04: ancestor-path tagging (tag a cached entry with its own album id + every ancestor id via `Album::ancestorsOf()`) so an ancestor's tag eviction reaches descendants without a runtime tree walk. **User correction:** there is no native cache-tagging primitive available (default `file` driver) — "tags" are hand-rolled key-list bookkeeping (a tag is a cache key whose value is a set of member keys), mirroring `RouteCacher::rememberTags()`/`forgetTag()`'s existing pattern, reimplemented independently.
- Q-052-05: user-group membership change is in scope as an invalidation trigger (new `UserGroupMembershipChanged` event, third gap found to match).

**Spec is now feature-complete** (FR-052-01..11, NFR-052-01..05, S-052-01..12, full Interface & Contract Catalogue including two new events `AccessPermissionChanged`/`UserGroupMembershipChanged` and two new listeners `ManagedCacheAlbumInvalidator`/`ManagedCacheUserInvalidator`). Directory renamed `052-query-cache-service` → `052-managed-cache-service` to match the generic naming resolution. The album-invalidation listener also evicts a mutated album's immediate-parent tag, closing a "negative cache" gap (a child becoming newly visible/hidden must still invalidate the parent's cached children list even though that list never referenced the child).

### Feature 048 – Fix Multi-Group Permissions — Spec/Plan/Tasks Drafted (prior session, 2026-07-01)

**Bug report:** A user who belongs to two groups on the same album (e.g. "All" = View only, "Support_VIP" = View+Access+Download) only received the grants of whichever group's `AccessPermission` row was created first. Reordering the shares flipped the outcome.

**Root cause:** `BaseAlbumImpl::current_user_permissions()` (`app/Models/BaseAlbumImpl.php:261-271`) uses `Collection::first()` to pick a single matching `AccessPermission` row instead of merging every matching row.

**Resolution direction (Q-048-01, resolved — Option A):** Collect every matching row (direct-user row + every row for a group the user belongs to) and OR each of the 5 boolean grant flags. No precedence between direct-user and group rows — most permissive always wins, matching the existing pattern already used elsewhere (`AlbumPolicy` ORs `current_user_permissions()` with `public_permissions()`; `canDeleteById`/`canEditById` already OR across groups in SQL).

**Follow-up design decision (user-requested):** instead of returning a synthetic `App\Models\AccessPermission` Eloquent instance (which is inherently persistable — mass-assignable, `save()`-able), the merged result is a new `App\DTO\EffectiveAccessPermission` (`final readonly class`, plain DTO, matches the existing `CheckoutDTO`/`PixelSizeAssignment` style). This makes "cannot be persisted by accident" a type-level guarantee (NFR-048-03). `current_user_permissions()`'s return type changes accordingly across `BaseAlbumImpl`, the `BaseAlbum` trait, and `@property` docblocks on `Album`/`TagAlbum`/`PersonAlbum` (FR-048-04).

**Key constraint:** Zero new DB queries (NFR-048-01) — `access_permissions` is already eager-loaded via `BaseAlbumImpl::$with`, and `$user->user_groups` is already read by the current (buggy) code, so the fix is a pure in-memory `Collection` merge.

**Not yet done:** Implementation (I1–I7 in plan.md / T-048-01–11 in tasks.md), ADR-0004, quality gates.
